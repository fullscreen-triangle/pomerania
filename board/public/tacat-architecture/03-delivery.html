Build and delivery

Two stages in the Dockerfile, four in the pipeline, nine jobs. The organising claim is narrow and testable: a container image can build perfectly while the graph inside it is wrong — so three of the gates check data rather than code, and the last one runs the image that was actually pushed.

Every gate here exists because a specific defect got past the ones before it. That history is the most useful thing on this sheet, and it is tabulated at the bottom.

The Dockerfile: reasoning happens once, on the other side of a wall

The builder stage installs a JVM because Owlready2 shells out to HermiT. The runtime stage installs no Java at all and copies only the finished artefact. This is the same seam sheet 01 is organised around, expressed as image layers.

What deliberately does not cross the wall: the JVM, the dev group, and the build cache. The image starts with the graph already materialised, so it answers an inferred type from plain SPARQL with no reasoner in the request path.

The pipeline: three of the gates check data, not code

Nine jobs across four stages, and the image is built only if everything before it passes. The middle stage is the point — ruff, mypy and bandit tell you the code is well-formed, and say nothing whatever about whether the graph is right.

Jobs run left to right; the image is built only if the middle stage passes, and is then run by the stage after it. Kaniko rather than docker-in-docker because a build job should not need more privilege than the build actually needs.

What is still unproven

This pipeline is green on a self-hosted instance, and the brief specifies gitlab.com. A green pipeline on one instance is not a green pipeline on another, and that evidence does not transfer — it was the single blocking defect in the predecessor submission.

What has been done about it: the CI file no longer contains anything instance-specific, so the same pipeline is provable here before the move. There are no runner tags; Kaniko needs no privileged runner; and smoke — the one job that could not have ported — now reaches the pushed image through a services: container addressed by alias rather than through the host Docker socket, which gitlab.com's hosted runners do not offer. services: is a core CI feature on the docker and kubernetes executors, so the job is byte-identical on both.

SOURCE_REPOSITORY is likewise no longer hard-coded. It reads CI_PROJECT_URL, so the graph's prov:wasRevisionOf names whichever host actually built it, and the most dangerous line in the migration checklist has stopped existing.

What remains is genuinely only a swap: a gitlab.com project, a token, and the documentation URLs in README.md, pyproject.toml, CITATION.cff and docs/index.md — which deliberately still point here, because pointing them at a project that does not yet exist would just be a different dead link. MIGRATION_TO_GITLAB_COM.md holds the runbook. Until it is done, step 5 of the brief is not evidenced, and no amount of refinement elsewhere substitutes for it.

Also honest about scope

The reproducibility claim is narrower than "reproducible build". What is proven is deterministic graph generation within a locked environment: two runs in the same CI job produce identical bytes. The Dockerfile still pulls a mutable base tag and resolves default-jre-headless through apt, neither of which is pinned by digest — so the container is not bit-reproducible at a later date, and the sheet does not claim it is.
