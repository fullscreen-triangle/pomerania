Identity and federation

"Reuse identifiers, never mint" is one slogan covering two different acts. Pointing at a ChEBI entry, a Rhea reaction or an EC number is class membership — those terms are classes, and our nodes are instances of them. Pointing at a UniProt protein is not: a protein is not an instance of a catalytic activity, it has one. So the first three are rdf:type and the fourth is UniProt's own up:enzyme, in UniProt's own direction.

This is also where the predecessor project failed. It carried every PURL as an xsd:string, so the graph advertised identifier reuse while being unjoinable: a federated query against its own nodes returns zero rows, silently.

The identifier is the type

ChEBI entries, Rhea reactions, UniProt EC numbers and SBO roles are all classes in their source vocabularies, and each node here is an instance of one. So class membership is the relation that is exactly true — it needs no invented predicate and no second copy: 

tacat:CHEBI_57972
    a          owl:NamedIndividual, tacat:AminoAcid,
               <http://purl.obolibrary.org/obo/CHEBI_57972> ;   # the identifier — a node, joinable, validated
    rdfs:label "L-alanine" .

It took three passes, and the middle one is the instructive part.

Identifiers were first carried only as an xsd:string — well formed, and completely unjoinable. That was fixed by adding skos:exactMatch and keeping the literal, justified by the claim that a literal is what sh:pattern can validate.

That premise is false. sh:pattern matches the lexical form of the value node; for an IRI, that is the IRI string, so it constrains IRIs perfectly well. Put the constraint on the object and run pyshacl: a well-formed PURL conforms, a wrong namespace and a locally minted term both violate. The literal never had a job the IRI could not do — it was redundant from the day it was justified.

skos:exactMatch was wrong independently, for the reason given further down this page for the protein links: SKOS mapping properties are sub-properties of skos:semanticRelation, whose domain and range are both skos:Concept. And the subject was an owl:NamedIndividual while the object is an owl:Class — an individual asserted as an exact match for a class, which is a category mismatch rather than a looseness.

Found by reading the prose against the code, which is also how the SERVICE blacklist was caught. Two further adversarial rounds then caught the fix — first too loose, so a malformed anchor beside a correct one conformed silently; then too tight, rejecting rh:Reaction and every dashed EC hierarchy node UniProt publishes. Written up in IDENTIFIER_LINKING_FIX.md.

① and ② are rdf:type. ③ is not — and the arrow runs the other way, because a protein is not a near-synonym for a catalytic activity.

Three targets, three judgments

TargetPredicateWhy this one
ChEBI entity rdf:type A ChEBI entry is an owl:Class; our node is one instance of it. Class membership is exactly true — no invented predicate, no second copy.
Rhea master rdf:type Same shape, and it is what resolved a previously conceded compromise: our reaction is an individual and Rhea's is an OWL class, which is precisely why rdf:type fits and skos:exactMatch did not.
UniProt EC class rdf:type A up:Enzyme class with the EC hierarchy as rdfs:subClassOf. Our enzyme node is an instance of the leaf.
UniProt protein up:enzyme The one that is not class membership. A protein is not an instance of a catalytic activity — it has one. The source's own relation, in the source's own direction.

Why the third one is not a matter of taste. SKOS mapping properties are sub-properties of skos:semanticRelation, whose domain and range are both skos:Concept (SKOS Reference §10, S19/S20/S40). So X skos:closeMatch Y entails that both ends are skos:Concept.

An earlier revision wrote enzyme skos:closeMatch protein — which asserted that seven UniProt protein records are concepts in a thesaurus. That is an inferred type on someone else's resources, in someone else's namespace. Nothing materialised it here, because SKOS is never imported — but any harvester merging the SKOS vocabulary and running RDFS entailment would derive it.

up:enzyme also carries the many-to-many honestly, which was the original objection to using a SKOS mapping property: P17174 catalyses both EC 2.6.1.1 and 2.6.1.3, and simply gets two up:enzyme triples.

Why not owl:sameAs anywhere. sameAs would license a reasoner to merge everything ChEBI asserts about the species into this graph — a far stronger claim than "these denote the same thing", and it would make the local A-Box hostage to an import we never validated.

The join happens at Rhea, not here

The payoff for all of the above is one question the local graph cannot answer alone: which organisms express an enzyme catalysing these reactions? It works only because the identifiers are nodes.

Nothing is fetched or joined in our process. We send one query to Rhea; Rhea issues the SERVICE call to UniProt and returns rows already joined. Both endpoints are SIB-hosted, which is why federation is reliable in that direction.

Why federation is refused in the request path

Federation is a CLI concern — tacat federate — never a request-path one. A SERVICE clause in a submitted query would make the server fetch a caller-chosen URL and hand back the response — server-side request forgery rather than a feature. The endpoint refuses it; see sheet 01 for where QueryPolicy sits.

The module also degrades to a checked-in cached result and says so loudly. A live demo that depends on someone else's endpoint being up is a demo that fails in front of an audience — so the counts above are a cached snapshot, not a timeless fact.

The failure this design exists to prevent

Two ways to be wrong, both silent. The predecessor project stored every PURL as an xsd:string — so a join against its own nodes matched nothing, and returned zero rows without erroring. It also cited neutral-parent ChEBI identifiers (CHEBI:16015, L-glutamic acid) where Rhea uses the microspecies (CHEBI:29985, L-glutamate(1−)). Both are real, well-formed, resolvable identifiers. Both produce an empty result rather than an error.

A test that checks an accession is well-formed proves nothing about whether the graph is joinable. So the suite asserts the identifier arrives as a URIRef rdf:type, and a companion test fails if any external PURL is reintroduced as a literal — and, since a URIRef can still be the wrong one, CQ10 and CQ11 assert the (label, identifier) pair against hand-written expectations, so a transposed or neutral-parent identifier fails the build. See sheet 02 for the competency-question machinery.

Three identifiers that are counterintuitive

EntityThe trap
L-cysteineThe bare name resolves to CHEBI:17561, a tautomer. These reactions use CHEBI:35235. Resolving a ChEBI ID from a name string is unsafe.
Pyridoxal 5′-phosphateThe cofactor is the dianion CHEBI:597326, which is what UniProt's COFACTOR line cites — not the neutral parent CHEBI:18405.
L-alanineCHEBI:57972 is "L-alanine zwitterion" in ChEBI while Rhea prints "L-alanine". Charge suffixes also use U+2212 MINUS SIGN while the L- prefix is an ASCII hyphen — the same string contains both, and naive joins fail silently.
