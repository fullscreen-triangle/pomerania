The request path

One SPARQL query, from the socket to the response body. GET and POST differ in how they obtain two strings — the query and the Accept header — and in how each refuses a request that carries neither, then converge on one pipeline of four phases. Two of those phases are decisions and two are work, and both decisions live in modules that have never heard of HTTP.

Sheet 01 draws this as a single box below the build/run seam: a finished graph, served without a reasoner. This sheet opens the box. The parts worth the space are the lexical scanner that decides read-only — which has now been wrong four times, in both directions — and the fact that a running server is not evidence that a graph loaded.

Phases 1 and 4 are the decisions; 2 and 3 are the work. Both decisions live in modules that import no web framework and name no status code: api/policy.py raises PolicyViolation, api/negotiation.py raises NotAcceptable, and api/app.py is the only file that knows either of those is a 400 or a 406. That is what lets both be tested without a client — and it is why the scanner below could be attacked directly, in a unit test, rather than only through HTTP.

2. The scanner, and the four times it has been wrong

Read-only is a whitelist on the query form: the first bare keyword must be one of SELECT, ASK, CONSTRUCT, DESCRIBE. "Bare" means outside IRIs, string literals and comments — the three places a keyword-shaped run of letters can appear without being a keyword. Deciding that needs a scanner, because those tokens contain each other's delimiters: # is legal and common inside an IRI (<…rdf-schema#>), so stripping comments with a pattern truncates the prologue and makes a valid query unparseable.

The same scan answers the second question — does any bare keyword equal SERVICE? A federated clause makes this server fetch a URL the caller chose and hand back the response, which is server-side request forgery rather than a feature.

It has been wrong in both directions, and every time it was found by reading rather than by the tests.

Over-refusal, once. It began as re.compile(r"\bSERVICE\b", re.IGNORECASE) — a blacklist over raw text, sitting one function away from a docstring explaining that a blacklist over raw text is unsound. SELECT ?service is a legal query with no federated clause and it was refused; so was SERVICE inside a comment, a literal, or an IRI path segment — and the case-insensitive flag caught a lower-case service in prose too. The scanner replaced it.

Under-refusal, three times — and all three are the same bug. A skip ran further than it should have and carried the keyword away inside it.

  1. The < operator. Every < was read as opening an IRI, so FILTER(1 < 2) started a skip that ran to the next > — past the clause. Fixed in 8f94207 by validating the span against the characters SPARQL rule [139] forbids inside an IRIREF.
  2. The prefixed name. Resuming the scan on the local part let ex:prefix re-enter the declaration branch, whose skip-to-> did the same thing.
  3. The escaped quote. The literal skip used str.find, which cannot see a backslash escape:
SELECT ?o WHERE { FILTER(?o != "\"") SERVICE <http://169.254.169.254/…> { ?s ?p ?o } }

In "\"" the search stops at the escaped quote, closing the literal one character early; the real closing quote then opens a second, unterminated literal whose skip runs to end of input and takes the SERVICE clause with it. The scanner yields [SELECT, WHERE, FILTER] and the policy accepts the query.

That one was exploitable, and the symptom hides it. The query is valid SPARQL, so rdflib accepts it and the clause executes. Against a loopback listener the server made a POST to the caller-chosen host — and the caller still received a 400, raised afterwards by rdflib failing on the response — but only when the target returns something rdflib cannot parse. Against a target that speaks SPARQL the endpoint answers 200, with the target's data handed back verbatim. A refusal that arrives after the request has already gone out looks exactly like a refusal that prevented it.

The fix walks the literal honouring ECHAR escapes, and raises UnterminatedLiteral if it never closes. contains_service_clause turns that into True — a refusal — because the tail the scanner could not reach is precisely where a smuggled clause sits. query_form carries the same guard, though it rarely fires: it returns on the first bare keyword, so it usually abandons the generator long before the unterminated literal is reached. The refusal comes from the SERVICE check, which has to drain the whole stream.

Where that fix actually is, as at 30 July 2026. It was found after the submission deadline, so it sits on the branch fix/service-scanner-escape on the development remote — not on main, and not in the published repository or the image in the registry. The submitted code still has the hole this section describes.

And it stays that way. The published version is what was submitted and shared; changing it now would change the thing being assessed. So the fix is not a pending merge — it is evidence about how the defect was found, which is the only reason it is worth writing down. The table below describes the fixed behaviour, which is what the branch's tests assert; the assessed artefact behaves as the paragraphs above it describe.

The pattern worth naming. All three under-refusals have the same shape: a skip that ran further than it should and carried the keyword away inside it. The scanner's whole job is to decide what is bare, and every bug in it has been a token it wrongly decided was not. A fourth would most likely be the same shape again — which is why the regression cases are named "smuggled behind X" rather than one test per syntax feature, and why the interesting question about this module is not "is it right?" but "what else can start a skip?"

3. Negotiating a query result: two branches, four media types

The endpoint implements the read subset of the SPARQL 1.1 protocol, so stock clients work: it reads Accept, q-values included, to choose a representation, and returns a 406 for what it cannot produce rather than answering in a format nobody asked for.

Two honest qualifications, because "honours Accept" would overclaim. q-values order the candidates and never exclude one, so text/csv;q=0 on a SELECT still returns CSV — RFC 9110's "q=0 means unacceptable" is not implemented. And the graph branch deliberately answers Turtle with a 200 for any of six requested types, three of which are concrete non-graph formats: compatibility bought at the cost of strictness, because a SPARQL client sets Accept before it knows the query form.

There is also a third negotiation in this service that the figure does not cover: GET / chooses HTML or JSON with "text/html" in accept.lower() — a substring test, not a ranking. It answers text/html;q=0 with HTML. That is fine for a console door and would not be fine for the results endpoint.

Order matters more than it looks. The sort is stable, so entries of equal q keep their header order, and the loop breaks on a wildcard rather than skipping past it. So Accept: */*, …+xml returns JSON while Accept: …+xml, */* returns XML, on identical q-values. Together with the CSV branch raising from inside the loop, the order the header was written in decides real outcomes.

4. What the diagram cannot show

You might assumeThe thing worth knowing
A running server means a loaded graph It does not. If startup fails, build_app logs and serves an empty graph rather than crashing, so the process is up either way. GET / reports the same counts, but with a 200 on them; only /health turns the difference into a status code. It has two 503s, and they catch different things: an empty graph — which is what the startup fallback trips — and a non-empty graph with nothing inferred, which is the --no-reason artefact that parses and serves perfectly while carrying nothing the reasoner derived. The second is the interesting one.
/health is a cheap ping It runs three SPARQL COUNT queries and two len() calls — one directly, one inside graph_stats. GET / runs the same three counts and one len(). Fine at ~390 triples, and not a pattern to carry to a real store.
/health returns plain text Only when it passes. It is declared PlainTextResponse, but its 503s are raised as HTTPException and therefore arrive as JSON.
/validation fails with a failing status It never returns a status that judges the graph: a violating graph is conforms: false and missing shapes is conforms: null, both with a 200. It reports; it does not judge. An unreadable shapes file is a different matter — only the missing case is guarded, so a parse failure there escapes as a 500.
Everything runs off the event loop Nearly. The plain def handlers run wholly in a threadpool, which Starlette arranges for you. POST is async def, so only run_query is handed off explicitly — its body read, content-type dispatch and empty-query 400 all run on the loop. rdflib is synchronous and CPU-bound, so that is the part that had to move.
Every phase turns its failures into a status Phase 2 catches Exception, so anything rdflib raises becomes a 400. Phase 4 catches only NotAcceptable — so a serialiser failure that is not a negotiation failure escapes as a 500. _decode's RuntimeError is the documented one, and it is documented as unreachable. The asymmetry is real; whether it matters depends on trusting that word.
An error always looks like an error Not to a browser. A 500 is produced by ServerErrorMiddleware, which sits outside CORS, so it carries no CORS header and the browser reports an opaque network failure instead. Every handled status — 400, 406, 422, 503 — is produced inside CORS. (And CORS only acts at all on a request carrying an Origin: a curl gets no such header on any status.)

Where federation went. There is no SERVICE in the request path by design, but the federated query still exists — as tacat federate, run from the command line against the built graph. Sheet 04 covers what it joins and why it works at all. One decision seen from two sides: the endpoint has no third-party dependency at request time, and the demo still gets to show a live join.
