07 · Federated querying

A language that closes the seam by refusing to be a query language at all.

A biological question spanning more than one public database is today answered by a script: a host-language program that interpolates identifiers into query strings, sends them, parses what returns, and interpolates again. The host language knows nothing about the data and the query language knows nothing about control flow — and every failure mode of federated retrieval lives in the seam between them.

The observation the design rests on

The databases a biologist must cross — a reaction knowledge base with a SPARQL endpoint, a protein resource exposing both SPARQL and REST, a pathway resource exposing only flat-file REST, an ontology available as a downloadable artefact — do not share a query model, and no amount of engineering will give them one.

But they do share a result model

Finite sets of identifiers carrying attributes. So a language whose terms denote result sets, and whose operators denote instructions on what to do with a result, is portable across backends in a way that a language whose terms denote graph patterns can never be. That object is a plan language — and queries are its leaves, never written by the user.

Compilability decided before any request is issued

A backend is characterised by what it can answer. Lowering a plan step is total exactly on the steps whose required capabilities are contained in the source's declared set — so a plan admits a static capability check that decides compilability before any request goes out.

What that converts

A whole class of runtime failures becomes compile-time diagnostics. You learn that a plan cannot be served — and which capability is missing from which source — without touching the network, waiting on a timeout, or half-populating a result set.

Six verdicts, not a boolean

Conventional query interfaces return rows. A plan executor returns one of six distinguishable verdicts, and the theorem is that any interface returning rows alone conflates at least two of them — the same argument as elsewhere in this work, in a new setting.

The verdict that only exists in federation

Starvation

A step that failed because an earlier step under-retrieved. It is reachable only in the federated setting — a single database cannot produce it — and the paper argues it is the characteristic failure of federation rather than an exotic case. Today it is invisible: the second query simply returns fewer rows, and nothing says why.

Identifier translation — where the real losses are

This is the part that will be familiar from practice. Cross-namespace maps are partial, non-injective and non-confluent. Three results follow.

ResultWhat it means at the bench
Exact composition laws for retention You can compute what fraction of a set survives a translation chain, in advance, from the maps themselves.
Translation loss is not recoverable by reordering Rearranging which namespace you cross first does not buy the loss back. It is not an optimisation problem.
Two plans differing only in translation route may return different sets — without either being wrong Two pipelines crossing the same three databases by different routes legitimately disagree. Today that reads as a bug in one of them.
The consequence for reproducibility. If two plans can legitimately disagree because they crossed namespaces differently, then a result is not reproducible without its translation route. That is a provenance requirement no current federated pipeline records, and it follows from the mathematics rather than from engineering sloppiness.
