Chapter 3

Asking questions

SPARQL has far fewer moving parts than it looks like it does. The goal for one sitting: read your own queries aloud and explain each line.

★★★ must know 15 min SPARQL · federation you will demo this live

1. The whole idea

A SPARQL query is a pattern with holes in it. Write triples as you would write data, but put a variable — a word starting with ? — wherever you do not know the value. The engine finds every set of values that makes the pattern true.

You already know this

It is a motif search. You describe a shape — [ST]-x(2)-[DE] — and the tool returns every position that matches. You are not writing instructions for how to search; you are describing what a hit looks like. SPARQL is that, over facts instead of residues.

2. Anatomy of a query

LineWhat it does
PREFIXThe same abbreviations as in the data file. Purely shorthand.
SELECT ?enzyme ?ecWhich variables come back — the columns of the answer table.
WHERE { … }The pattern. Everything inside is triples with holes.
?e a tacat:Enzyme"find anything that is an Enzyme, call it ?e". Note ?e is not in the SELECT — it is a working variable that connects the lines.
;  .Exactly as in Turtle: same subject again; end of statement.
a ?ec + FILTERThe enzyme's other types, kept only when the IRI is a purl.uniprot.org/enzyme/ one. This is the point of the question: the classification comes back as a node in someone else's graph, not a string we invented.
ORDER BYSort. Matters more than it looks — see §5.
If you have met SQL

SELECT … WHERE is borrowed deliberately. The difference: SQL's WHERE filters rows of a named table; SPARQL's is a shape to match, and there are no tables at all. The engine works out the joins from the variables you reuse — reusing ?e on three lines is the join.

Why this is the payoff

That extra line is only writable because participation is a node with a role on it. With the naive hasSubstrate/hasProduct model, the role is baked into the property name — you could ask one question or the other, but never filter, combine or count by role.

The n-ary bridge earns its complexity here, in one line of difference between two answers.

4. The other query forms

FormReturnsUse
SELECTa tablealmost everything
ASKtrue / false"is there any reaction that…?" — used in tests
CONSTRUCTa new graphextract a subset as RDF to hand to someone else
DESCRIBEa graph about one node"tell me everything about this thing"

The service supports all four. It does not support INSERT, DELETE or DROP — the update half of the language. Chapter 5 has a caveat about how read-only that really is.

5. Federation: one question, two databases

Here is where reusing identifiers stops being a principle and starts paying rent.

The local graph knows three reactions. It knows nothing about which organisms express enzymes catalysing them — that is UniProt. A federated query asks both at once, using SERVICE to delegate part of the pattern to a remote endpoint and joining the results.

Verified live on 27 July 2026:

15reviewed proteins · RHEA 17441
27reviewed proteins · RHEA 19453
91reviewed proteins · RHEA 21824
The FAIR argument, demonstrated rather than asserted

This query works only because the local graph uses the same Rhea IRIs UniProt uses. Had the project invented its own reaction identifiers — or stored the real ones as text rather than as links — there would be nothing to join on, and it would return an empty table.

Every README in the world claims to follow FAIR principles. This is a two-second demonstration that the "I" is real.

Two traps that cost real time

Trap 1 — Rhea models reactions as classes, not individuals

The natural thing to write is ?rhea a rh:Reaction. It returns nothing. Rhea models each reaction as an OWL class, so the correct pattern is ?rhea rdfs:subClassOf rh:Reaction. Getting it wrong produces an empty result rather than an error.

Trap 2 — a LIMIT on an ordered join is a correctness bug

An earlier version capped the detailed query at LIMIT 25 for speed. Results were ORDER BY ?rhea and reaction 21824 sorts last — so the cap cut it off entirely. A demo whose whole point is "all three reactions federate" would have shown two, with nothing to indicate anything was missing.

A truncating limit on an ordered join is not a performance knob.

And one engineering decision

The summary query returns in about a second; the per-protein detail query takes ~43 seconds because the join fans out. More importantly, both depend on someone else's server being up.

The module therefore caches its result and degrades loudly — if SIB is down it says so and serves the cached answer rather than hanging or silently returning nothing. A live demo depending on a third-party endpoint is a demo that fails in front of an audience.

They might ask: isn't a live external dependency bad for reproducibility?

Yes, and it is handled. The federated tests are marked network and deselected by default, so the build never depends on the internet; the cache makes the demo deterministic.

Dropping the federation entirely would remove the only working demonstration that identifier reuse buys anything — so the right answer is to isolate it, not delete it.

6. What to be able to say

The 30-second version

"The competency questions are SPARQL, and they run as tests. The pair worth looking at is CQ05 and CQ06: 'which reactions have L-glutamate as a participant' returns four, 'which produce it' returns three, and they differ by one line — a filter on the participant's role. That difference is only expressible because participation is a node rather than a property. And the federated query joins the local graph to live UniProt on shared Rhea identifiers, which is the FAIR interoperability claim demonstrated rather than asserted."
