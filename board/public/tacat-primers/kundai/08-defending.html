Chapter 8

Defending it

A narrative that holds together, the questions most likely to come, and the weak points worth naming before someone else does.

★★★ the night before quiz mode below 11 questions glossary

1. The governing rule

Any line you cannot explain is a liability, not an asset

The assessment is of your coding ability, and the decision rests on a live discussion of "the details and challenges". A smaller submission you fully own beats a larger one you cannot discuss.

If a question lands on something you genuinely do not know, the right answer is "I don't know — here is how I would find out". It costs far less than a confident wrong answer given to someone who has published on the topic.

4. Questions to expect

What does the OWL buy you here that RDFS wouldn't?

This is the question, and v0's honest answer was "nothing". Now: a defined class with necessary and sufficient conditions, so reaction type is derived rather than asserted. RDFS can express a hierarchy; it cannot express "anything with these four features is a transamination", which is what makes classification possible. Then show the inference and the negative control.

Why an n-ary participant node rather than Reac4Cat's role pattern?

Because it carries stoichiometry, which the role pattern does not. I know Reac4Cat took the BFO role route with educt-mixture and product-component-set groupings; if the requirement were alignment with their upper-ontology commitments rather than inspectable coefficients and roles, I would switch. BioPAX and SBML both use the bridge pattern, and it is W3C's Use Case 1.

Why not import EMMO, or Reac4Cat itself?

Importing a large upper ontology means inheriting its commitments — every axiom comes with it, and either you honour them or your graph is quietly inconsistent with the thing you imported. For a three-reaction demo that would be decoration at best. Demonstrating awareness of it in the decision record is more honest than inheriting it unused.

Is rdflib not just an in-memory store? This wouldn't scale.

Correct, and the README says so. rdflib was specified in the brief, it holds about 390 triples in-process, and it is not comparable to Fuseki, GraphDB or Oxigraph. The migration path is a repository seam — the query layer does not care what is behind it. Claiming production equivalence would be the wrong answer; naming the seam is the right one.

Why is PLP not a reaction participant?

It is an enzyme-bound cofactor. It cycles PLP → PMP → PLP and is regenerated rather than consumed, so it does not balance into the equation — in the resting enzyme it is an internal aldimine with an active-site lysine, and during catalysis an external aldimine with the substrate. Rhea's equations for all three reactions have exactly four participants and none is PLP; UniProt records it as a COFACTOR on the protein, citing CHEBI:597326, the dianion. Modelling it as a fourth substrate would validate perfectly and be chemically false.

How do you know your identifiers are right?

Each was checked individually against its primary database, not resolved through a cross-reference. That matters: the earlier version resolved ChEBI IDs via KEGG's conv/chebi, which returns the neutral parent — so every wrong ID was off by exactly one hydrogen per unit of charge, systematically. Three of the nine are counterintuitive and all three are documented inline, including that the bare name "L-cysteine" resolves to a tautomer.

Did the reasoner prove the dehydrogenase is not a transamination?

No — it failed to derive that it is one. Under the open-world assumption those are different claims. The code computes the excluded set as a subtraction, which is a closed-world reading; the precise statement is "HermiT did not derive it, because the roles are wrong".

Why both OWL and SHACL? Isn't that redundant?

They answer opposite questions. OWL infers under an open world, SHACL validates under a closed one. Given owl:maxCardinality 1 on a licence with two licences asserted, an OWL reasoner does not complain — it infers owl:sameAs between them, silently declaring CC-BY and CC0 identical. SHACL reports a violation. Same data, opposite outcome.

Why mint tacat:CHEBI_29985 instead of using the ChEBI IRI directly?

So that this project's own assertions — labels, roles, class membership — do not attach to ChEBI's identifier, which would make the graph appear to be making claims about ChEBI's term. The link is rdf:type: the ChEBI term is a class and our node is an instance of it, so class membership is the relation that is exactly true. Not owl:sameAs, which would license a reasoner to merge the two descriptions entirely; and not skos:exactMatch, which entails both ends are skos:Concept and pointed an individual at a class. Using the PURL directly as the node is equally standard and simpler; that much is a genuine trade-off rather than a settled question.

Why is the reasoning at build time?

Because reasoning needs a JVM and takes time, and the service does not need to reason — it needs to answer. The builder stage installs Java, runs HermiT once, and materialises the inferred types into Turtle; the runtime stage copies that and installs no Java at all. The container then starts with the graph loaded, needs no network, and answers an inferred type from plain SPARQL. If reasoning fails, the image does not build.

What would you do next?

All four things this used to name are shipped — reproducibility is a CI job, read-only is QueryPolicy, provenance carries the commit SHA and a source checksum, and GET /validation exists. So the honest answer is now about the model, and every item comes from something found in it: stop hand-asserting the premises — HermiT is told which molecules are 2-oxo acids by a curated list, and a SHACL check against ChEBI's own hierarchy, fetched at build time, would close that without importing forty thousand classes; make the class a hierarchy so ω-transaminases classify, α- and ω- as siblings under a parent requiring only the amino-group transfer; replace the global AllDisjoint with a local closure over the nine entities actually carried, because as a general claim it is false; and named graphs, so provenance is per-triple rather than per-dataset — which is what matters the moment data arrives from more than one instrument.

5. The weak points, stated plainly

Each is better volunteered than discovered. None is fatal; all become strengths when raised first.

Four of these were fixed, and that is now the better story

Reproducibility, the read-only contract, provenance content and runtime validation were all open when this chapter was first written. All four are closed — and describing the shape of each fix is stronger than having never had the gap:

  • Reproducibility — reproducible-build builds twice and compares bytes.
  • Read-only — was correct only because rdflib’s parser rejected updates; it is now a QueryPolicy that decides, with tests.
  • Provenance — carries the commit SHA and a checksum of the reference data. Not a timestamp: that would have broken byte reproducibility.
  • Validation — GET /validation makes SHACL conformance observable at runtime, not only asserted in CI.

The last two constrain each other, and saying so out loud is the kind of detail that reads as having actually built it.

7. Glossary

A-Box
The individuals layer — the specific facts. "Assertions."
API
A fixed set of requests a program accepts, plus a promise about the responses.
bandit
A tool that scans Python for common security mistakes.
CI/CD
Continuous integration: a server rebuilds and re-checks the project on every change.
competency question
A question the ontology must answer, written before building. Here they are also the tests.
container / image
An image is the frozen, exactly-defined artefact; a container is a running instance of it.
content negotiation
The caller states what format it wants via Accept; the server obliges or returns 406.
defined class
A class with necessary and sufficient conditions, so a reasoner can recognise instances rather than only check them.
federation
One query answered across several endpoints, joined automatically. The SERVICE keyword.
FastAPI
The Python web framework used. Generates its own API documentation.
graph
A set of triples. Nothing more.
HermiT
The OWL reasoner used. Written in Java, which is why the build needs a JVM.
IRI
A globally unique name that is also a web address.
JSON-LD
RDF written as JSON, for consumption by ordinary web tooling.
literal
A plain value — text, number, date. A dead end in the graph.
lock file
The exact versions the project was built with. The lot number, not the catalogue number.
mypy
Checks that Python type annotations are consistent, before the code runs.
n-ary relation
A relationship among more than two things. Needs a bridge node, because a triple only holds two.
ontology
A vocabulary plus logical statements a reasoner can compute over.
open-world assumption
Unstated means unknown, not false. How OWL reasons.
OWL
Web Ontology Language. The logic layer above RDF.
Owlready2
The Python library used to build the ontology and drive HermiT.
pytest
The Python testing tool. 182 tests here, across eight files.
RDF
The model in which every fact is a subject–predicate–object triple.
rdflib
The Python RDF library. Holds the graph in memory and answers SPARQL.
reasoner
A program that derives everything else that must be true from a set of logical statements.
regression test
A test that stops a fixed bug from coming back.
ruff
A fast linter and formatter for Python.
SHACL
Shapes Constraint Language. Validates RDF under a closed world. Run with pyshacl.
SPARQL
The query language for RDF. Pattern-matching over triples.
SSRF
Server-side request forgery: making a server issue requests on an attacker's behalf. Why SERVICE is refused.
T-Box
The class layer — the terminology, as opposed to the specific facts.
triplestore
A database for triples that answers SPARQL.
Turtle (.ttl)
The human-readable file format for RDF used throughout.
uv
The Python packaging and environment tool used. Also the assessor's own.
uvicorn
The web server that runs the FastAPI application.
