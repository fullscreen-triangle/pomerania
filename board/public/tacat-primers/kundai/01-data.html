Chapter 1

Facts as data

Before anything can be reasoned over, queried or served, the facts have to be written down in a form a machine can join to other people's facts.

★★★ must know 15 min RDF · IRI · Turtle will be asked

1. Why not a spreadsheet?

You could put three reactions in a table in five minutes and everyone could read it. So why the machinery?

a. A table has a fixed shape; reactions do not

Your columns are substrate_1, substrate_2, product_1, product_2. Fine for these three.

Now add glutamate dehydrogenase — three substrates, three products. Now a coefficient of 2. Now two cofactors. Each time you either add columns that are empty for most rows, or start cramming lists into cells, at which point only a human can read it.

b. Merging a table with someone else's costs a negotiation, every time

This is the important one. Your column is substrate. Rhea's is participant. UniProt does not have it at all. Tables can be integrated — but somebody has to map the schemas and reconcile the keys first, by hand, for each new pair.

c. A table cannot say what its words mean

Your cell says L-glutamate. Which one — the neutral acid, or the singly-charged anion at physiological pH? The string cannot tell you, and the machine cannot ask.

What RDF is for

RDF makes global identifiers and shared vocabularies part of the data model, so two graphs produced independently join automatically when they reuse the same terms. That is the entire purpose, and the odd syntax and the URLs-as-names are in service of it.

The honest qualifier: RDF removes the per-pair negotiation, not the need for agreement altogether. Two graphs that use different vocabularies for the same idea still need mapping. What changes is that the agreement lives in a shared vocabulary, once, rather than in a bespoke reconciliation for every pair of datasets.

2. The triple

RDF has exactly one kind of statement. It has three parts.

You already know this

A triple is a lab-notebook line made machine-readable: sample 7 — OD600 — 0.42. Subject, what was measured, value.

The discipline RDF adds: the subject and the predicate are not free text. They are globally unique names someone else can also use.

3. IRIs: names that are also addresses

If two people are to combine their facts, they must use the same name for the same thing. RDF solves this by making every name a URL.

Only the third has the property that matters: if two datasets anywhere in the world use that IRI, they are provably talking about the same molecule — no negotiation, no mapping table. That is the trick, and it is why the project reuses ChEBI, Rhea, UniProt and SBO identifiers.

You already know this

You would never write "the aspartate one" in a methods section — you would write the accession. An IRI is that instinct made mandatory and machine-readable. Paste http://purl.obolibrary.org/obo/CHEBI_29985 into a browser and ChEBI's page loads. The name is the address.

Why not invent our own names?

Because a name only helps if others use it. OBO Foundry principle FP-005: terms out of scope should be imported from the appropriate ontology. Minting your own :Water instead of CHEBI:15377 means your data can never join anyone else's — which defeats the purpose of RDF.

Worth knowing, because it is arguable

This project does create a local name per chemical — tacat:CHEBI_29985 — and then links it to the official ChEBI IRI. The alternative is to use ChEBI's IRI directly as the node.

Both are standard. Linking keeps this project's own statements off ChEBI's identifier, so the graph never appears to make claims about ChEBI's term; using it directly is simpler and more obviously "reuse". Be able to state the trade-off rather than pretend it is settled.

4. Turtle: the readable way to write triples

RDF is an abstract model, not a file format. The project uses Turtle (.ttl), the one designed for humans.

@prefix tacat: <…> An abbreviation. tacat:REACT_0000002 is the full IRI — shorthand, nothing more. Same idea as CHEBI:29985.

Notice something in the real file

The built graph types each reaction as tacat:TransaminationReaction — and nobody wrote that. No line of code asserts it. A reasoner derived it and it was written into the file afterwards. That is Chapter 2, and it is the centrepiece of the submission.

5. Why the names look like REACT_0000002

It would be more readable as tacat:AlanineTransaminaseReaction. It is deliberately not.

Every serious vocabulary here does the same: ChEBI (CHEBI_29985), the whole OBO Foundry (GO_0006103), EMMO, and NFDI4Cat's own Voc4Cat (voc4cat_0000123).

The reason: a label can change and an identifier cannot. With a readable IRI you have two bad choices when terminology moves — change the IRI and break everyone who linked to it, or keep an IRI that contradicts its own label. With an opaque number you change the rdfs:label and nothing breaks.

6. Literals vs IRIs — the distinction that mattered

An object can be one of two things, and this is the most consequential thing in the chapter.

an IRI

<http://…/CHEBI_29985>

A node — a thing in the graph. Can be linked to and from. Joins to other datasets.

a literal

"http://…/CHEBI_29985"

A value — text. A dead end. Never joins to anything.

The difference is two quotation marks. Visually almost nothing. Functionally, the difference between a working knowledge graph and a very tidy text file.

This actually happened

An earlier version stored every ChEBI, Rhea and EC identifier as a string. The file looked right. The identifiers were correct and well-formed. A test confirmed they were present and correctly shaped.

It took two more passes to fix properly, and the middle one is the part worth knowing. The first fix carried both forms — an IRI so joins work, plus the string so validation could pattern-match it. The premise was that sh:pattern needs a literal. That premise is false: sh:pattern matches the lexical form of the value node, and for an IRI the lexical form is the IRI string. The duplicate was buying nothing.

So the second fix deleted it. What is left is one triple, and it is not a link property at all — rdf:type.

Why rdf:type, and not owl:sameAs or skos:exactMatch?

Because it is the relation that is exactly true. In ChEBI, Rhea, UniProt and SBO the external term is a class, and each node here is an instance of one — so class membership needs no invented predicate.

owl:sameAs is far stronger: it licenses a reasoner to pull everything ChEBI asserts into your graph, and everything you assert into ChEBI's. skos:exactMatch is weaker but wrong in a different way — it is a concept-scheme mapping property, so it entails both ends are skos:Concept, and here it pointed an individual at a class. For linking to a database you do not control, the claim that is simply accurate beats both.

7. What was deliberately avoided: blank nodes

RDF lets you write a node with no name — useful for intermediates nothing else refers to. The participant bridge nodes of Chapter 2 are exactly that, so blank nodes were the obvious choice.

They were rejected, for two practical reasons:

  • An unnamed node cannot be cited — a validation report saying "this node is wrong" needs something to point at.
  • Unnamed nodes duplicate silently when graphs merge, because nothing can tell the machine your anonymous node and mine are the same one.

Hence PART_0000002_01: ugly, and addressable.

8. The vocabulary, so the words stop being scary

WordWhat it actually is
RDFThe model: all facts are triples. Not a file format.
Turtle / .ttlA readable file format for RDF. Used throughout.
RDF/XMLAn older format for the same thing. Verbose; still common in ontology tooling.
JSON-LDRDF as JSON, for ordinary web tooling. Dörr's own SciDatS uses it.
IRI / URI / URLFor your purposes the same thing: a unique name that is also an address.
LiteralA plain value. No outgoing links.
Namespace / prefixAn abbreviation for a long IRI stem. Exactly the CHEBI: in CHEBI:29985.
GraphA set of triples. That is the entire definition.
TriplestoreA database for triples that answers SPARQL. Here it is rdflib, in memory inside the running program — fine for ~390 triples, not a production store, and the README says so.
They might ask: why RDF rather than a graph database like Neo4j?

Both store networks. But a Neo4j SUBSTRATE_OF relationship means whatever your team decided it means — joining to another lab's Neo4j needs a human. RDF makes every node and every relationship a globally resolvable IRI, so two graphs from two institutions merge by construction.

For a FAIR-data project that property is the requirement. For an internal application with no external integration, Neo4j would often be the better engineering choice.
