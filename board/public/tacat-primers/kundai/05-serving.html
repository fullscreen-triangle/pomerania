Chapter 5

Serving it

A graph on a laptop helps nobody. Here is the twenty minutes of HTTP you need — and the one decision that separates "I wired up a web framework" from "I implemented a protocol".

★★ good to know 12 min HTTP · API · SPARQL protocol one open item

1. What an API is

An API is a fixed set of requests a program will accept, and a promise about what it sends back. Nothing more.

You already know this

A liquid-handling robot has a command interface: a documented list of instructions, in a defined syntax, each with defined effects. You do not open the machine to move liquid — you send aspirate(well=A1, volume=50) and it holds up its end.

The value is the contract: anything that speaks the syntax can drive the machine, and the internals can be rebuilt without breaking the callers.

2. HTTP in ten minutes

A client sends a request, the server sends a response, the exchange ends. Four parts to a request:

PartWhat it isExample
Methodthe verbGET, POST
Pathwhich resource/sparql, /health
Headersmetadata about the requestAccept: text/csv
Bodythe payloadthe query text

GET means "give me something and change nothing" — safe to repeat. POST means "here is data, do something with it", used when the payload is too big for a URL. Long SPARQL queries go by POST.

Why the distinction matters

400 is "your sample arrived mislabelled — fix the label and resubmit". 500 is "the instrument caught fire". Both mean no result, but they tell you completely different things about what to do next, and they route to different people.

A service returning 500 for a typo is lying about whose problem it is — and generating an alert for the operator at 3am over a user's missing bracket. The submission returns 400 for a malformed query. A small thing that reads as professional.

3. What FastAPI and uvicorn are

uvicorn — the server

Listens on a network port, accepts connections, speaks raw HTTP. Knows nothing about SPARQL or chemistry.

FastAPI — the framework

Your Python code, organised so a function is attached to each path. Knows nothing about network sockets.

uvicorn receives the request and hands it to FastAPI, which routes it and hands the answer back. Both were specified in the assignment.

FastAPI has one property worth knowing: it generates its own interactive documentation from the code. /docs is a live page listing every endpoint with a "try it" button — free, and it means the API documents itself rather than drifting from a hand-written README.

4. The decision that matters: implement the standard

The brief asked for "a SPARQL endpoint via an API". The minimum reading: accept a query string, return some JSON. That works, and nothing else in the world can talk to it.

There is a published W3C standard — the SPARQL 1.1 Protocol — specifying how a SPARQL service should behave over HTTP. Implementing that means every existing SPARQL client works unmodified: YASGUI, curl, SPARQLWrapper, rdflib's remote store.

Why this is the professional signal

"I built an endpoint" and "I implemented the protocol so your existing tools work" are different claims, and the second is checkable in ten seconds by pointing any SPARQL client at it.

It also is the FAIR "A" — accessible by a standard protocol — rather than a README assertion about it.

Content negotiation

The same query returns different formats depending on what the caller asks for, via the Accept header: four media types — SPARQL-results JSON by default, SPARQL-results XML, CSV on request, and Turtle for queries returning a graph.

The XML one has the best story, and it is worth volunteering: it was added because a stock SPARQL client asked for it and got JSON with a 200 on it. "A client asking for XML should get XML or a 406, not JSON that it cannot parse." That is the kind of bug only an external client can find, which is the argument for implementing the protocol rather than an API that resembles it.

One subtlety fixed after review: asking for CSV when the query is an ASK (true/false, not a table) is a request that cannot be satisfied. That is 406 Not Acceptable, not 500 — again, whose fault it is.

5. The endpoints

PathPurpose
GET /Landing page: ready-to-run examples and graph statistics.
GET|POST /sparqlThe endpoint proper.
GET /healthA liveness probe — machine-readable "am I working?", fails if the graph is empty. The Dockerfile's HEALTHCHECK calls it and marks the container unhealthy; something above it has to act on that. Nothing here does.
GET /validationThe SHACL report for the graph being served — so conformance is observable, not merely asserted in CI.
GET /docsAuto-generated interactive API documentation.
The trap — an advertised query that does not parse

v0's landing page listed an example containing res:reaction/ALT ta:hasSubstrate ?s. That is invalid SPARQL — an abbreviated name cannot contain an unescaped /.

So the most likely first action of any reviewer — copy the example, run it — returned an error, from a test suite that was entirely green. The fix is four lines: a test that executes every advertised example.

6. One real security hole, and why it was there

Recall SERVICE from Chapter 3: it makes the query engine fetch data from another server. Extremely useful for federation — and a serious problem in an endpoint that accepts queries from anyone.

The fix is a policy decision, not a patch: federation runs from the command line, never from the request path. The service refuses any query containing a SERVICE clause. The federated query still exists and still runs — as tacat federate, deliberately, by whoever holds the shell, not by an anonymous caller.

The guard has been wrong four times — and one is still live

Read-only is now a decision, not an accident. QueryPolicy whitelists the four read forms explicitly and DECISIONS.md records why. That gap is closed — do not volunteer it, or the correction comes from him.

The SERVICE guard is the one that keeps moving. Four times wrong: once over-refusing — a regex rejected the legal SELECT ?service WHERE … — and three times under-refusing, each the same bug, a skip that ran too far and swallowed the clause. A < comparison read as an IRI; a prefixed name whose local part re-entered the IRI branch; and an escaped quote that closed a literal one character early.

The third is live in the submitted code. Verified end to end: the server made an outbound request to a caller-chosen host. The caller still gets a 400, raised afterwards by rdflib — but only when the target returns something rdflib cannot parse. Against a target that speaks SPARQL the caller gets 200 and the target's data. Full SSRF with exfiltration, not blind. Fixed on a branch that will not be merged, because the published repository is what was assessed.

Volunteer this one, if the conversation earns it. Every one was found by reading the code against the prose, never by a test — which is the more useful observation about where the tests are weak.

One more, briefly

Queries originally ran on the server's main event loop, so one expensive query blocked every other request — including /health, meaning a slow query could make the container report itself unhealthy. They now run off the main loop. The kind of thing that never shows up with one user and takes a service down with ten.

7. What to be able to say

The 30-second version

"It implements the read subset of the SPARQL 1.1 protocol rather than a bespoke endpoint, so stock clients — YASGUI, curl, SPARQLWrapper — work against it unmodified. GET, POST-as-body and POST-as-form, with content negotiation across SPARQL-results JSON, XML, CSV and Turtle. Malformed queries return 400 rather than 500, and every example query advertised on the landing page is executed by the test suite. SERVICE clauses are refused: federation is something I do at build time, not something an anonymous caller does through my server."
