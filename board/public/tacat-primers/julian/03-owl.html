Chapter 3

OWL & inference

This is the chapter with no analogue in your stack. OWL classes are not types you assign — they are sets defined by conditions, and membership is computed by a theorem prover. Slow down here; everything that makes this project more than a database with URLs for keys is in §3.

1. T-Box and A-Box

The vocabulary splits an ontology into two halves. It maps loosely onto schema and data, and the places where the mapping fails are the interesting ones.

T-Box (terminological)A-Box (assertional)
Containsclasses, properties, axiomsindividuals and their facts
Roughlyyour schema / type definitionsyour rows
In this projectsrc/tacat/ontology/schema.pysrc/tacat/ontology/population.py
Enforced on write?No. Nothing rejects data that contradicts the T-Box. This is the first place the schema analogy breaks

Two more terms you will meet immediately. A class is a set of individuals. An individual is a thing in the world (tacat:REACT_0000002 — one specific reaction). A property is a binary relation; object properties point at individuals, data properties point at literals.

A place the type-system intuition actively misleads

In TypeScript, declaring class Reaction and never instantiating it is fine and inert. In OWL, declaring domain and range on a property is not a constraint — it is an inference rule. Writing tacat:hasCofactor with domain = [Enzyme] does not mean “reject anything that isn’t an Enzyme”. It means “anything appearing on the left of this property is thereby inferred to be an Enzyme.”

So a typo does not raise an error; it silently adds a type. That is the single most common misreading of OWL by developers, and it is the reason SHACL exists as a separate standard.

2. The open-world assumption

Every database you have used assumes a closed world: the data is complete, so absence of a row means the fact is false. SELECT … WHERE NOT EXISTS is a meaningful question with a definite answer.

OWL assumes an open world: the data is a partial view of reality, so absence means unknown, not false.

Closed world — your database 
SELECT 1 FROM cofactor
WHERE  enzyme_id = 'EC_2_6_1_2';
-- 0 rows

-- Conclusion: this enzyme has no cofactor.

The absence of the row is the answer.

Open world — OWL 
# No hasCofactor triple for this enzyme.

# Conclusion: we do not know whether this
# enzyme has a cofactor. Possibly it does
# and nobody has written it down yet.

The absence of the triple means nothing at all.

This is not perversity. It is the correct semantics for the actual situation: your graph describes three reactions out of tens of thousands, and there is no sense in which it is complete. ChEBI, Rhea and UniProt are all incomplete too, permanently and by design.

The three consequences that matter
  • OWL cannot validate. “This field is required” is unexpressible — a missing value is never a violation, it is missing information. Hence SHACL.
  • A reasoner only ever adds. It derives new entailed facts; it never rejects the input. The only thing it can report as wrong is a logical contradiction.
  • “Not inferred” is not “inferred not”. This one comes back in §5 and is a live nuance in this project.

3. Necessary versus sufficient — the whole idea

Here is the crux. There are two ways to relate a class to a description, and the difference between them is the difference between a database and a knowledge graph.

Primitive class — necessary only 
tacat:Transamination
    rdfs:subClassOf tacat:Reaction .

If something is a Transamination, then it is a Reaction. A one-way implication. It tells you what follows from membership, and gives no way to determine membership.

Membership must therefore be asserted by hand — by a human, or by a loop in your code.

Defined class — necessary and sufficient 
tacat:TransaminationReaction
    owl:equivalentClass [ … conditions … ] .

Something is a TransaminationReaction if and only if it satisfies these conditions. A two-way implication.

Membership is now decidable: hand any individual to a reasoner and it works out whether it belongs.

The closest thing in your world

A TypeScript discriminated union tells the compiler how to narrow: given {kind: 'circle', r: number}, the compiler determines which branch you are in rather than being told. Or: a database VIEW whose WHERE clause defines membership — rows enter and leave it as the underlying data changes, without anyone tagging them.

OWL’s version is stronger than both, because the conditions can be arbitrary description logic — nested quantifiers over other classes and properties — and the engine that evaluates them is a full theorem prover rather than a pattern matcher.

The actual definition in this project

Reproduced from ontology/schema.py (build_schema; build.py only re-exports it). Owlready2 lets you write description logic as Python operator overloads, so & is intersection and .some() is the existential quantifier ∃: 

class TransaminationReaction(BiochemicalReaction):
    equivalent_to = [
        BiochemicalReaction
        & hasParticipant.some(
            ReactionParticipant & participatingEntity.some(AminoAcid)  & participantRole.value(reactant))
        & hasParticipant.some(
            ReactionParticipant & participatingEntity.some(TwoOxoAcid) & participantRole.value(reactant))
        & hasParticipant.some(
            ReactionParticipant & participatingEntity.some(TwoOxoAcid) & participantRole.value(product))
        & hasParticipant.some(
            ReactionParticipant & participatingEntity.some(AminoAcid)  & participantRole.value(product))
    ]

In English: a biochemical reaction that consumes an amino acid, consumes a 2-oxo acid, produces a 2-oxo acid, and produces an amino acid.

Chapter 6 explains why that shape is the chemical signature of a transamination — the amino group moves from donor to acceptor, so each class appears on both sides in opposite roles. What matters here is the engineering property: the conditions quantify over classes and roles, never over specific molecules. A definition written as “has CHEBI:57972 as a reactant” would classify exactly the three reactions it was reverse-engineered from and nothing else. This one generalises.

4. What a reasoner actually does

A description-logic reasoner — HermiT here; Pellet and ELK are the other names you will see — takes the T-Box and A-Box and computes the deductive closure. Three jobs:

1

Consistency checking

Is there any possible world in which all these axioms hold at once? If two axioms contradict, the ontology is inconsistent and the reasoner raises. In this project that is a hard build failure, not a warning.

2

Classification

Work out the full subclass lattice, including subsumptions nobody declared. If class A’s conditions logically entail class B’s, then A ⊑ B whether or not you said so.

3

Realisation

For every individual, compute every class it belongs to. This is the step that does the work here.

Run it and the reasoner reports: 

$ tacat infer

  Asserted as transamination before reasoning:
    (none - nothing was asserted)

  Inferred by HermiT after reasoning:
    + alanine transaminase reaction
    + aspartate transaminase reaction
    + cysteine transaminase reaction

  Not derived (roles do not match the definition):
    - glutamate dehydrogenase reaction (negative control, partial)

Nothing in the source asserts that any reaction is a transamination. add_reaction() builds plain BiochemicalReaction individuals with participant nodes. The type in the Turtle file is computed.

5. The negative control is the load-bearing part

A defined class that recognises exactly the instances you built it for proves nothing — you could have written equivalent_to = {r1, r2, r3} and got the same output. What distinguishes a definition from an enumeration is a case designed to fool it.

Glutamate dehydrogenase is that case. It contains both headline molecules of the transaminations — the two anyone would name if asked what these reactions are about — with their roles reversed:

The three transaminationsThe dehydrogenase control
L-glutamate (an amino acid)productreactant
2-oxoglutarate (a 2-oxo acid)reactantproduct

Checked against the four conjuncts:

ConjunctSatisfied by the control?
consumes an amino acidyes — L-glutamate
produces a 2-oxo acidyes — 2-oxoglutarate
consumes a 2-oxo acidno
produces an amino acidno

Two of four fail, so it is not derived. Any definition keyed on which molecules are present would have swallowed it whole. But be precise about why it fails, because the honest version is weaker than the obvious one.

The control is excluded on arity, not on role

REACT_0000099 is modelled with exactly two participants — L-glutamate in, 2-oxoglutarate out — of a six-species reaction. Four conjuncts need four role-slots filled, and two participants cannot fill four. The reasoner never reaches the role comparison.

The role discrimination is real all the same: a four-participant reaction with the roles reversed is refused, verified. That is the control this should have been. As shipped, it does not demonstrate the thing it is cited for.

The honest caveat, and it is worth knowing

demonstrate_inference() computes the excluded set as a set difference — all_reactions - transamination.instances(). That is a closed-world read of an open-world result. Under OWA, failing to derive membership is not a proof of non-membership.

So “HermiT proved it isn’t a transamination” is an overclaim. “HermiT did not derive it, because the roles do not match the definition” is exact. The distinction is small and someone will ask about it.

6. Reasoning at build time, not query time

Reasoning is expensive — description-logic reasoning is at least EXPTIME for the expressive profiles, and HermiT is a Java program Owlready2 shells out to. You do not want that in a request path.

So the project runs it once, at build, and materialises the results: the derived rdf:type triples are written into data/reactions.ttl. The API then answers ?r a tacat:TransaminationReaction from plain triple matching, with no reasoner anywhere near the request.

You know this pattern

It is a materialised view, or an ahead-of-time compile. Pay the expensive computation once at build, ship the result, keep the runtime cheap. The Dockerfile makes it structural: the builder stage installs a JVM and runs HermiT; the runtime stage copies only the resulting Turtle and installs no Java at all. If reasoning fails, the image does not build.

Two traps in the materialisation, both real bugs

  • Owlready2 files reasoner output in a separate internal ontology. Inferences land in http://inferrences/ inside the World, so onto.save() silently drops every derived type — the artefact looks fine and contains nothing inferred. The fix serialises the whole World, not the ontology.
  • Serialising the World drags in Owlready2’s own bookkeeping. That produced three owl:Ontology headers in one file, so OWL tooling picked one arbitrarily and attached owl:versionIRI to the wrong one. Those two internal headers are stripped explicitly.

7. Why CI asserts that the inference fired

A consistency check is not enough. A defined class that classifies nothing is perfectly consistent — the empty set satisfies every axiom. So a broken definition passes a consistency check in silence, and the whole point of the project evaporates without any signal.

The pipeline therefore asserts the counts:

result = demonstrate_inference()
assert result["asserted_before"] == [],            "transamination must never be asserted"
assert len(result["inferred_after"]) == 3,         "expected 3 inferred"
assert len(result["correctly_excluded"]) == 1,     "the negative control must not be derived"

Three assertions: nothing was asserted, exactly three were derived, the control was not. That is the difference between a gate and a decoration — and it is the same instinct as testing that your cache is actually being hit rather than that the cache code runs.

Chapter 3 in five lines
  • Open world: a missing triple means unknown, not false. OWL therefore cannot validate.
  • subClassOf is necessary only; equivalentClass is necessary and sufficient, which makes membership computable.
  • A reasoner checks consistency, classifies, and realises — it only ever adds facts.
  • The negative control is what distinguishes a definition from an enumeration.
  • Reason at build time, materialise the result, keep the runtime free of Java.
