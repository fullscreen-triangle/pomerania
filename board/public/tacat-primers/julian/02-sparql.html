Chapter 2

SPARQL & the protocol

SPARQL is close enough to SQL that you will be productive in an hour. The two things worth real attention are that joins happen implicitly through repeated variable names, and that SERVICE lets a query reach across the internet into somebody else’s database mid-execution — which is both the payoff of this project and a server-side request forgery hole if you expose it.

1. It is SQL, with the joins moved

A SPARQL query is a set of triple patterns. A triple pattern is a triple with variables (?x) in some positions. The engine finds every set of bindings that makes all the patterns true simultaneously.

SQL 
SELECT e.label, p.chebi
FROM   reaction   r
JOIN   participant p ON p.reaction_id = r.id
JOIN   entity      e ON e.id = p.entity_id
WHERE  r.label = 'alanine transaminase reaction';

Joins are explicit. You name the tables, then state how they connect.

SPARQL 
SELECT ?entityLabel WHERE {
  ?reaction rdfs:label "alanine transaminase reaction" ;
            tacat:hasParticipant ?p .
  ?p        tacat:participatingEntity ?e .
  ?e        rdfs:label ?entityLabel .
}

No JOIN keyword. ?p appearing as the object of one pattern and the subject of the next is the join.

The mental swap

Think of every triple pattern as a row in one gigantic three-column table (subject, predicate, object) — because that is literally what a triplestore is. Then a SPARQL query is a self-join over that table, and repeating a variable name is the join condition. Once you see it that way, the rest of the syntax is decoration.

The rest maps directly: FILTER is WHERE’s predicate part, OPTIONAL is LEFT JOIN, and DISTINCT, ORDER BY, GROUP BY, LIMIT, OFFSET, COUNT, UNION all mean what you expect.

SQLSPARQLNote
JOIN … ON(repeat a variable)implicit; the commonest source of accidental cross-products
LEFT JOINOPTIONAL { … }unbound rather than NULL
WHERE x > 3FILTER(?x > 3)applies to bindings, not to matching

2. Four query forms, not one

SQL has one shape of result: a table. SPARQL has four forms, and two of them return a graph rather than rows.

FormReturnsResponse media typeNearest thing you know
SELECTa table of bindings application/sparql-results+json SELECT
ASKa single boolean application/sparql-results+json SELECT EXISTS(…)
CONSTRUCTa new RDF graph text/turtle a view, or a response-shaping serialiser
DESCRIBEwhatever the server thinks describes a node text/turtle SELECT * — deliberately underspecified

CONSTRUCT is the interesting one and has no clean SQL analogue: it runs a query and emits triples built from the bindings, so the output is itself a graph you can feed into another query. It is the composability that makes graph pipelines work.

3. Property paths

This is genuinely absent from SQL, and once seen it explains a lot of otherwise-cryptic queries. A property path traverses several edges in one pattern, with regex-like operators: 

# exactly this chain of three predicates
?protein up:annotation/up:catalyticActivity/up:catalyzedReaction ?rhea .

# one or more hops up a class hierarchy
?class rdfs:subClassOf+ tacat:ChemicalEntity .

# either direction
?a tacat:catalysedBy|^tacat:catalysedBy ?b .

+ is the one to notice: recursive traversal of arbitrary depth, in one line. In SQL that is a recursive CTE. In this domain — where classifications are deep trees, like the EC hierarchy in chapter 6 — it comes up constantly.

4. Two real queries from the project

These are the pair that justify the whole n-ary bridge-node design from chapter 1. Same molecule, same graph; the only difference is one extra line.

CQ05 — which reactions have L-glutamate as a participant?

SELECT DISTINCT ?label WHERE {
    ?reaction a tacat:BiochemicalReaction ;
              rdfs:label ?label ;
              tacat:hasParticipant ?participant .
    ?participant tacat:participatingEntity tacat:CHEBI_29985 .
} ORDER BY ?label

4 rows — the three transaminases, plus the glutamate dehydrogenase control.

CQ06 — which reactions produce it, in the left-to-right orientation?

SELECT DISTINCT ?label WHERE {
    ?reaction a tacat:BiochemicalReaction ;
              rdfs:label ?label ;
              tacat:hasParticipant ?participant .
    ?participant tacat:participatingEntity tacat:CHEBI_29985 ;
                 tacat:participantRole tacat:Product .
} ORDER BY ?label

3 rows — the dehydrogenase drops out, because there L-glutamate is consumed rather than produced.

Why this pair is the demo — stated carefully

The bridge node is not required merely to ask whether something is a product. A binary model could answer that directly with ?reaction tacat:hasProduct tacat:CHEBI_29985, and claiming otherwise is an overclaim a reviewer will take apart.

What the bridge node buys is that one participation becomes a first-class object: the role is data rather than a predicate name, a stoichiometric coefficient has somewhere to live, evidence and provenance can attach to it, the same query shape works for every role, and SHACL can validate it and cite it in a report. The 4-versus-3 difference is the visible demonstration; the justification is that participation has properties of its own.

5. Federation: a JOIN across the internet

SERVICE tells the engine to evaluate part of the pattern against a remote endpoint and join the results back in. It is a foreign data wrapper, except the foreign database is a public research server in Switzerland and you did not have to ask anyone.

The project’s live federated query, in full

SELECT ?rhea ?equation (COUNT(DISTINCT ?protein) AS ?proteinCount)
WHERE {
  VALUES ?rhea { <http://rdf.rhea-db.org/21824>
                 <http://rdf.rhea-db.org/19453>
                 <http://rdf.rhea-db.org/17441> }

  ?rhea rdfs:subClassOf rh:Reaction ;
        rh:equation     ?equation .

  SERVICE <https://sparql.uniprot.org/sparql> {
    ?protein up:annotation/up:catalyticActivity/up:catalyzedReaction ?rhea ;
             up:reviewed true .
  }
}
GROUP BY ?rhea ?equation
ORDER BY ?rhea

Run against Rhea’s endpoint, this returns in about a second:

Rhea masterReviewed proteins
1744115
1945327
2182491

The local graph knows nothing about organisms or proteins. It never will. But because every reaction carries a real Rhea IRI rather than a locally invented identifier, the question “which organisms express an enzyme catalysing these reactions?” is answerable without any ETL, data copy, or agreement with SIB. That is what identifier reuse buys, demonstrated rather than asserted.

Three ways this bites, all found the hard way
  • rdfs:subClassOf rh:Reaction, not a rh:Reaction. Rhea models reactions as OWL classes, not individuals. Getting this wrong returns an empty result set rather than an error — the recurring theme.
  • A LIMIT on an ordered federated join is a correctness bug. An earlier revision limited the detail query to 25 rows. Because the join fans out and the results were ordered, that silently returned only two of the three reactions. It looked like a complete answer.
  • Latency is a demo risk. The aggregate above takes ~1 s; the per-protein detail form takes ~43 s. The module caches its last good result and degrades loudly, because a live demo that depends on somebody else’s uptime is a demo that fails in front of an audience.

6. SERVICE is an SSRF vector — this is your territory

You will spot this faster than most people in this field do. If an unauthenticated endpoint accepts arbitrary SPARQL and evaluates SERVICE, then anyone can make your server issue arbitrary outbound HTTP requests to a host of their choosing. Cloud metadata endpoints, internal services, port scanning by timing — the standard SSRF catalogue, delivered through a query language.

The project’s API refuses SERVICE clauses in submitted queries outright. Federation is a build-time and demo-time concern, executed deliberately, not something a caller gets to trigger. That refusal, and the read-only contract around it, live in src/tacat/api/policy.py.

This was a real finding, and it is worth knowing how it started. An earlier revision did reject INSERT DATA, DELETE WHERE and DROP ALL — but only because rdflib’s Graph.query() parser does not accept update syntax. Nothing in the project decided it. Had a future rdflib merged its grammars, an unauthenticated endpoint bound to 0.0.0.0 would have quietly become writable.

It is now a QueryPolicy that classifies the query form and refuses anything that is not SELECT, ASK, CONSTRUCT or DESCRIBE, with tests/test_policy.py covering it. The distinction matters more than the fix: correct by accident and correct by policy look identical from outside and behave differently under a dependency upgrade.

A place your instincts are ahead of the domain

“Read-only” being a property of a third-party parser rather than an enforced policy is exactly the kind of thing a web engineer flags on sight and an ontologist does not. Worth saying out loud — it is a genuinely open item, and identifying it is a point in your favour rather than an admission.

This is your territory, so know that the guard has been wrong four times

Once over-refusing: it began as re.compile(r"SERVICE", re.IGNORECASE), a blacklist over raw text, which rejected the perfectly legal SELECT ?service WHERE …. A scanner replaced it.

Three times under-refusing, and all three are the same bug — a skip that ran further than it should and carried the keyword away inside it: a < comparison read as an IRI opener; a prefixed name whose local part re-entered the declaration branch; and a backslash-escaped quote that closed a literal one character early, so the phantom literal that opened swallowed the rest of the query.

The third is live in the submitted code. Verified end to end against a loopback listener: the server made an outbound POST to a caller-chosen host. The caller still receives a 400 only when the target returns something rdflib cannot parse; against a target that speaks SPARQL the answer is 200 with the target's data handed back. The 400 case is the one that looks like the guard working. Fixed on a branch that will not be merged, because the published repository is the artefact under assessment.

The useful observation is not the bug — it is that every one was found by reading the code against the prose, and none by a test.

7. The SPARQL 1.1 Protocol is just HTTP

“Provide a SPARQL endpoint” does not mean “accept a query string in a bespoke JSON body”. There is a W3C protocol specifying the HTTP binding, and implementing it means stock clients — YASGUI, rdflib’s SPARQLStore, curl, any of the visual query builders — work against your service unmodified. That is the difference between publishing data and publishing an API only you can call.

Three request forms the spec requires

GET /sparql?query=SELECT%20%3Fs%20WHERE%20%7B...%7D
Accept: application/sparql-results+json

POST /sparql
Content-Type: application/x-www-form-urlencoded

query=SELECT+%3Fs+WHERE+%7B...%7D

POST /sparql
Content-Type: application/sparql-query

SELECT ?s WHERE { ... }

Plus content negotiation on the way out: application/sparql-results+json by default, text/csv if asked, text/turtle for the graph-producing forms. And correct status codes — a malformed query is a 400, not a 500, because the fault is the client’s.

Ordinary web engineering, and it counts

This is the one part of the project where your existing instincts are directly, immediately correct. The form-encoded variant is also why python-multipart is a runtime dependency rather than a test one: FastAPI implements it with Form(), and Form() raises at app-construction time if the package is missing. It does not degrade — the process fails to start.

Two smaller things the API does that are worth knowing about because they were bugs first: queries run in a thread pool rather than on the event loop (one expensive query used to block every other request, including /health), and asking for text/csv on an ASK result returns 406 rather than crashing, because a boolean has no CSV representation.

8. The queries are the test suite

One methodological point, because it is the part most tailored to the assessor. In ontology engineering, competency questions are the specification: you write down the questions the model must be able to answer before building it, and the model is finished when it answers them.

This project ships them as executable tests — each question carries its SPARQL and its expected answer set, so the specification and the regression suite are the same artefact. CQ01–CQ04 are quoted verbatim from NFDI4Cat’s own published biocatalysis question set, which the assessor wrote.

It also ships OUT_OF_SCOPE_QUESTIONS — the questions from that set this model deliberately cannot answer, each with what it would require. Kinetics needs quantities with units; purification needs a laboratory-process model. Knowing where a model stops is the point of writing competency questions at all.

  • Four query forms; two return graphs, and CONSTRUCT is what makes pipelines compose.
