Chapter 4

SHACL & validation

SHACL is the constraint layer you were expecting OWL to be — closed-world, rejects bad data, produces an error report naming the offending node. It maps almost one-to-one onto JSON Schema. The reason it exists as a separate standard, rather than as a feature of OWL, is the point of this chapter.

1. Why a second standard was necessary

Recall from chapter 3: OWL is open-world, so a missing value is unknown rather than wrong, and a reasoner only ever adds facts. That makes “this field is required” literally inexpressible. Every practical RDF deployment needs that check anyway, so for roughly a decade people misused OWL for it and got quietly wrong results. SHACL was standardised in 2017 to do the job properly.

Can it reject input?only if logically contradictoryyes, that is the entire purpose

The example that settles it

Take a dataset with owl:maxCardinality 1 on dcterms:license, and two licences asserted — CC-BY and CC0.

OWL does not complain. Under an open world with no unique-name assumption, the consistent reading is that the two IRIs must denote the same thing, so the reasoner infers owl:sameAs between them — silently declaring CC-BY and CC0 to be the same licence, and propagating that everywhere.

SHACL reports a violation. Same data, opposite outcome. This is the standard expert/novice discriminator in the field, and it is worth being able to state it cold.

2. Shapes are RDF, and read like a schema

A SHACL shape declares a target (which nodes it applies to) and a set of constraints. Here is the real shape guarding the bridge node from chapter 1, lightly trimmed: 

tacat:ReactionParticipantShape
    a sh:NodeShape ;
    sh:targetClass tacat:ReactionParticipant ;

    sh:nodeKind sh:IRI ;
    sh:message "Participant bridge nodes must be IRIs, not blank nodes."@en ;

    sh:property [
        sh:path     tacat:participatingEntity ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:nodeKind sh:IRI ;
        sh:message  "Each participant must reference exactly one chemical entity, by IRI."@en ;
    ] ;

    sh:property [
        sh:path     tacat:participantRole ;
        sh:minCount 1 ;
        sh:maxCount 1 ;
        sh:in       ( tacat:Reactant tacat:Product ) ;
        sh:message  "Role must be exactly one of tacat:Reactant or tacat:Product."@en ;
    ] ;

    sh:property [
        sh:path         tacat:stoichiometricCoefficient ;
        sh:minCount     1 ;
        sh:maxCount     1 ;
        sh:datatype     xsd:decimal ;
        sh:minExclusive 0 ;
        sh:message      "Exactly one positive stoichiometric coefficient is required."@en ;
    ] .
The same thing in Zod 
z.object({
  participatingEntity: z.string().url(),
  participantRole: z.enum(['Reactant','Product']),
  stoichiometricCoefficient: z.number().positive()
})

Identical intent. minCount/maxCount are required-and-single, sh:in is an enum, sh:datatype is the type.

What differs

sh:targetClass — the shape finds its own subjects by querying the graph, rather than being applied to a value you hand it.

sh:nodeKind sh:IRI — no JSON equivalent, because JSON has no notion of a node versus a string. This is the constraint that enforces “no blank nodes”.

The shapes are RDF, so you can query your validation rules with SPARQL.

The constraint vocabulary, in one table

SHACLMeans
sh:targetClassapply this shape to every instance of a class
sh:pathwhich predicate this property constraint is about
sh:minCount / sh:maxCountcardinality — 1/1 is “required, single”
sh:datatypeliteral type, e.g. xsd:decimal
sh:nodeKindsh:IRI, sh:Literal, sh:BlankNode
sh:inenum — value must be from this list
sh:patternregex, on literals only
sh:minExclusivenumeric bound
sh:classthe value must be an instance of a given class
sh:messagethe human-readable error text

3. The shape that makes a README claim executable

Chapter 1 said “reuse identifiers, don’t mint them” is the community rule. A README can claim that; a shape can enforce it: 

sh:property [
    sh:path                rdf:type ;
    sh:qualifiedValueShape [ sh:nodeKind sh:IRI ;
                             sh:pattern  "^http://purl\\.obolibrary\\.org/obo/CHEBI_[0-9]+$" ] ;
    sh:qualifiedMinCount   1 ;
    sh:qualifiedMaxCount   1 ;
    sh:message "Every chemical entity must be an instance of exactly one ChEBI class."@en ;
] ;

Mint a local tacat:Water with no ChEBI anchor and the build fails. Note what the path is: rdf:type. The identifier is not a separate property at all — the node is an instance of the ChEBI class, and that single triple is both the join and the thing validated.

This is the second version, and the first one’s reasoning was wrong

The identifier used to be carried twice: as an IRI so joins would work, and as an xsd:string copy, justified by “a regex cannot be run against a node”. That premise is false. sh:pattern matches the lexical form of the value node, and for an IRI the lexical form is the IRI string — which is exactly what the shape above relies on. The literal copy was never buying anything, and it was deleted.

And here is the limit of what a shape can prove

That regex confirms the identifier is well-formed. It cannot confirm the identifier is correct — CHEBI_99999999 passes cleanly. Checking the shape of an external reference tells you nothing about whether it points at the right thing, or at anything.

That gap is exactly where the first submission’s error lived, and chapter 7 is the full anatomy of it.

4. Negative fixtures: testing the tests

A validation suite that only ever sees valid data proves nothing — a shapes file that constrains nothing at all would pass every run of it. So the project ships twelve deliberately broken fixtures and asserts that each one fails. One parametrised test carries all twelve; it asserts non-conformance only, not the text of the report: 

@pytest.mark.parametrize(("bad_graph", "why"), BAD_CASES, ids=[...])
def test_shapes_reject_bad_data(bad_graph, why, shapes):
    conforms, _, _ = validate(bad_graph, shacl_graph=shapes)
    assert not conforms, f"shapes failed to catch it: {why}"

The twelve cases are no_role, blank_node, minted_chemical, negative_coefficient, sbo_enzyme_as_role, string_licence, chebi_twin_alongside_correct, invented_obo_ec, malformed_ec, rhea_curie, malformed_sbo and sbo_enzyme_as_role_type. The why string is the failure message pytest prints if the assert trips — it is not matched against the SHACL report.

Mutation testing, essentially

You break the input on purpose and assert the guard catches it. Same instinct as writing a test that your auth middleware returns 401 — testing only the happy path tells you the middleware runs, not that it does anything.

5. --metashacl: validating the validator

Here is the failure mode that gets its own flag. SHACL shapes are RDF, and RDF accepts any predicate on any subject without complaint. So a typo in a constraint name: 

sh:minCounts 1 ;    # <- should be sh:minCount

…is not an error. It is a triple with an unrecognised predicate, which the validator ignores. The shape is now weaker than you think, the suite is green, and nothing indicates that a constraint silently evaporated.

pyshacl --metashacl validates the shapes graph against SHACL’s own shapes-of-shapes definition, so the typo fails loudly. The project runs it that way in CI. Given the theme of this domain, running SHACL without --metashacl would be an odd omission — a silent-failure guard that itself fails silently.

6. Both, running as CI gates

OWL and SHACL are not alternatives, and the project uses each for what it is good at:

QuestionAnswered by
Is this reaction a transamination?OWL — computed from structure
Are these axioms mutually satisfiable?OWL — consistency check
Does every participant have a coefficient?SHACL
Is every chemical anchored on a ChEBI PURL?SHACL
Are the bridge nodes IRIs rather than blank nodes?SHACL
Does the dataset description declare a licence and a generating activity?SHACL

Both run in the verify stage, before the container image is allowed to build. That ordering is the design: a container image can build perfectly while the graph inside it is wrong, so the data gates come first and the image is a downstream artefact of them passing.

Two notes on scope

Validation is observable at runtime, not only in CI. GET /validation returns the SHACL report for the graph being served, and the validation logic sits in src/tacat/validation.py rather than in the HTTP layer — conformance is a property of the data, and it was in the endpoint only because that is where it happened to be needed. It also makes the OWL-versus-SHACL argument demonstrable live rather than a paragraph in a design document.

Not a large generated profile. DCAT-AP’s own shapes file is 2,217 lines of generated constraints. This one is 168 lines, hand-written, with an sh:message on every constraint — because a machine-generated default message is useless to whoever has to fix the data at 11pm.

Chapter 4 in four lines
  • SHACL is closed-world validation; it is the layer OWL structurally cannot provide.
  • Shapes are RDF and map cleanly onto JSON Schema, plus sh:nodeKind and sh:targetClass.
  • Negative fixtures test the guard; --metashacl tests the guard’s own spelling.
  • Well-formed is not correct. A regex on an external identifier proves nothing about what it points at.
