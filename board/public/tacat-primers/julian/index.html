Start here

Two unfamiliar things, and one of them isn’t the code

This primer covers the parts of the transaminase knowledge-graph project that a full-stack developer has no reason to have met: the RDF/OWL/SHACL/SPARQL stack, and enough enzymology to understand why the modelling decisions are what they are. Everything on the computing side is introduced as a delta from something you already use in production.

Assumes SQL, HTTP, a graph DB, Docker, CI Assumes no chemistry ~2.5 h end to end

1. What the project actually is

A small read-only service. You POST it a query in a standard query language; it answers from a graph of facts about three enzyme-catalysed reactions. Architecturally it is unremarkable — a FastAPI app over an in-process store, containerised, built by GitLab CI. If that were all, you would be done in an afternoon.

What makes it a real exercise is that each layer is required to prove something about the layer beneath it, and the domain it describes fails silently in ways your usual stack does not.

1

Verified reference data

Nine chemical entities, three EC numbers, three Rhea reaction IDs, seven UniProt accessions. Typed frozen dataclasses in one Python module, each value checked by hand against the primary database it came from.

→ proves the facts are real and traceable
2

An OWL ontology

A formal, machine-computable description of what a reaction is — its parts, and the roles those parts play. Think of it as a schema written in description logic instead of DDL.

→ proves the vocabulary is coherent and can classify
3

A graph, with a reasoner run over it

Instance data in that vocabulary. Then a logic engine (HermiT) derives conclusions nobody wrote down — the reaction types are inferred, never asserted.

→ proves the ontology does work rather than decorating
4

Validation and tests

SHACL shapes reject malformed data under closed-world semantics. Domain questions run as automated tests on every commit.

→ proves the graph answers what it claims to
5

A SPARQL endpoint

Implements the published SPARQL 1.1 Protocol, not a bespoke JSON API, so stock clients work against it unmodified.

→ proves the data is reachable by someone who isn’t you
6

A container, built by CI

Multi-stage image; the reasoner runs at build time so the runtime ships no JVM. Every gate above runs before the image is allowed to build.

→ proves the result reproduces off your laptop

2. What transfers, and what doesn’t

Being a full-stack developer helps enormously with steps 5 and 6 and almost not at all with steps 2 and 3. The honest map:

You already knowMaps ontoWhere it breaks down
Tables, rows, foreign keys Triples, subjects, IRIs There is no schema enforcing shape, and identifiers are global URLs rather than table-local integers
Neo4j / property graphs RDF graphs RDF edges carry no properties. This single limitation generates the project’s central modelling decision
SQL SPARQL Very close. Joins are implicit through repeated variable names; there are four query forms, not one
CHECK constraints, JSON Schema, Zod SHACL Almost a clean mapping — and it is not what OWL does, which is the single most common misconception
TypeScript types, class hierarchies OWL classes The real gap. OWL classes are sets defined by conditions, and membership is computed. Nothing in mainstream development works this way
REST, content negotiation, OpenAPI SPARQL 1.1 Protocol Transfers directly. This part of the project is ordinary web engineering
Docker, CI/CD, semver, lockfiles The same things Transfers directly
The one thing to internalise

Every mental model you have for a database assumes a closed world: if the row is not there, the answer is no. RDF and OWL assume an open world: if the triple is not there, the answer is unknown. Almost every surprise in this stack — why OWL cannot validate, why a reasoner infers rather than rejects, why SHACL had to be invented as a separate standard — comes from that one line.

3. The property that shapes the whole design

You are used to failures that announce themselves: a constraint violation, a 500, a type error, a failed assertion. This domain mostly does not do that.

Use the wrong chemical identifier and your federated query returns zero rows — not an error, an empty result set, which is indistinguishable from a correct answer to a question with no matches. Store an identifier as a string where a URL was needed and you get the same empty result. Write a logical class definition that matches nothing and the consistency checker passes it happily, because a class with no members is perfectly consistent.

The nearest thing in your world

A LEFT JOIN where you meant INNER, on a key whose type coerces — joining a VARCHAR column against an INT in a database that silently casts. Every query runs. Every row comes back NULL on the right-hand side. Nothing logs. You find out weeks later from a business report.

Now imagine the join key is a chemical identifier, the right-hand table lives at a URL owned by a European research institute, and the correct value differs from the plausible-looking wrong one by a single hydrogen atom. That is the actual bug that broke the first submission, and chapter 7 is about why it was undetectable from inside the code.

Read that way, the parts of the project that look over-engineered — SHACL shapes on a ~390-triple graph, a CI job asserting that the reasoner fired, a deliberately wrong negative-control reaction — are not gold-plating. Each one exists because the corresponding failure is invisible.
