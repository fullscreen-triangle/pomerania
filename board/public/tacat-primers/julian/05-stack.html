Chapter 5

Stores & the stack

The last computing chapter, and mostly familiar ground: where triplestores sit relative to the databases you know, why rdflib is the SQLite of this world, and the metadata envelope (DCAT + PROV) that describes the dataset rather than the chemistry.

1. Triplestores against the databases you know

SystemModelQueryScaleShape enforced?

Note the column that is uniformly “no”. RDF stores do not enforce shape, ever. It is not a maturity gap — it follows from the open-world model in chapter 3. Validation is always a separate, deliberate pass.

rdflib is SQLite, and that is the honest framing

In-process, no server, no network, whole graph in memory, zero operational cost, perfect for tests and embedded use, and not a production database. The brief asked for rdflib specifically, so this is the correct choice — but the README says plainly that it is an in-process demonstration store rather than claiming equivalence to Fuseki.

Practical limit is around 10⁶ triples before memory and query planning become the problem. This graph has roughly 390.

There is a GraphRepository seam, and the obvious argument for it is wrong. It is tempting to call it a portability abstraction — swap rdflib for Oxigraph behind the interface. That does not hold. DECISIONS.md said so under a heading cut in e7db6cd, when the record was trimmed to the modelling decisions; the argument is kept here because it is the interesting half: rdflib already ships SPARQLStore and SPARQLUpdateStore, so Graph(store="SPARQLStore") exposes the identical API. Migrating means constructing the graph differently, not implementing an interface, and a Protocol on top would be a second abstraction over an existing one.

The honest reason is legibility: the service depends on three operations, and stating that makes the dependency inspectable and testable without a web client. as_rdflib_graph() is a named escape hatch — pySHACL needs a concrete Graph — rather than a leak pretending not to be one. Knowing why an abstraction is not justified is worth more here than having one.

2. The service layer

Ordinary web engineering, which is why chapter 2 covered the interesting part (the protocol) and this section is short. The shape: 

def create_app(graph: Graph | None = None) -> FastAPI:
    ...

An application factory with an injectable graph — so tests construct an app over a fixture graph with no filesystem and no network. Testable by design rather than testable in principle.

RouteDoes
GET /service info, graph statistics, ready-to-run example queries
GET /healthliveness probe — fails if the graph is empty, which is the failure that would otherwise look healthy
GET /validationthe SHACL report for the served graph — conformance observable at runtime, not just gated in CI
GET /docsOpenAPI UI, free from FastAPI
GET|POST /sparqlthe SPARQL 1.1 Protocol endpoint

Every example query advertised on / is executed by the test suite. That sounds fussy until you know it was a real defect: the first submission served an example containing an unescaped / in a prefixed name, so a reviewer’s most likely first action — copy the advertised example, POST it — returned HTTP 400. An advertised query that does not parse is a defect a green suite will happily hide.

3. The build-time / run-time seam

artefacts.py exists to answer one question: where does the graph come from at startup?

1

Normal case — the artefact exists

data/reactions.ttl was written by tacat build (or by the Docker builder stage). Load it with rdflib. No JVM, no reasoner, fast start.

2

Fallback — a clean checkout

No artefact. Build and reason in-process, which does require a JVM on PATH. The log says so before it tries, rather than dying on an opaque subprocess error.

Inside the container only case 1 ever happens, by construction. That is what lets the runtime image ship no Java.

4. The image, and why it is multi-stage

# ---- builder: has uv, a JVM, and the dev toolchain
FROM ghcr.io/astral-sh/uv:python3.13-bookworm-slim AS builder
RUN apt-get install -y default-jre-headless
COPY . .
RUN uv sync --frozen --no-dev
RUN uv run tacat build --output data/reactions.ttl     # <- HermiT runs HERE

# ---- runtime: no JVM, no dev dependencies, non-root
FROM python:3.13-slim
COPY --from=builder /app/.venv /app/.venv
COPY --from=builder /app/data/reactions.ttl /app/data/
USER app
CMD ["uvicorn", "tacat.api:app", "--host", "0.0.0.0"]

Reasoning happens at image-build time; the runtime stage copies the result. Consequences worth stating: the container starts with the graph already loaded, needs no network, answers queries about inferred types with no reasoner in the request path, and — the important one — if reasoning fails, the image does not build.

A real bug worth knowing, because it is subtle

An earlier revision ran uv run inside the build stage after an earlier uv sync --no-dev. uv run re-syncs by default, which reinstated the dev group — so pytest, ruff, mypy and bandit all shipped into the runtime image despite the --no-dev that was supposed to prevent exactly that. The flag was present, correct, and silently undone by a later command.

5. CI: four stages, and the middle one is the point

StageJobsGates on
quality ruff check + ruff format --check, mypy, bandit the code
verify pytest; ontology consistency plus an assertion that the inference fires; reproducible-build — two builds, compared byte for byte; pyshacl --metashacl over graph and dataset description the data
build Kaniko image build, pushed to the GitLab Container Registry, tagged by commit SHA everything above passing
smoke the pushed image started as a services: container and asserted against over HTTP — not the source tree the artefact that actually shipped

Three of those verify jobs are data gates rather than code gates, and that distinction is the differentiator. Your usual pipeline proves the code is well-formed and the tests pass. It cannot tell you the graph inside the image is wrong — every conventional gate would be green while the chemistry was nonsense.

Two smaller conventions that carry more weight in a research context than a product one:

  • Tag by commit SHA, not only :latest. A moving tag is not a reproducible reference, and reproducibility is the entire claim the CI layer exists to support.
  • Kaniko rather than Docker-in-Docker. The right choice on shared GitLab runners — no privileged container required.
The gate that was missing, and why it mattered

Until 27 July nothing checked that the build reproduced. Two builds were byte-identical — verified by hand — but Owlready2 → HermiT → rdflib serialisation is exactly where set iteration order can drift, and the failure is invisible: the graph stays correct while quietly ceasing to be reproducible.

The reproducible-build job now builds twice and compares bytes, and tests/test_reproducibility.py asserts the same property plus the weaker isomorphism form. Byte equality rather than isomorphism because that is what a registry tag and a source checksum actually depend on. Reproducibility is the specific claim the whole container and CI layer exists to support, and it was the one thing nothing verified.

6. DCAT and PROV — metadata about the dataset

So far everything has described chemistry. There is a second, thin layer that describes the dataset itself: what it is, who may use it, and what produced it.

You already ship this 
{
  "name": "tacat",
  "version": "0.1.0",
  "license": "MIT",
  "repository": "…"
}

package.json. Machine-readable metadata about the artefact, separate from what the artefact does.

DCAT + PROV 
tacat:dataset a dcat:Dataset ;
    dcterms:title   "Transaminase reactions"@en ;
    dcterms:license <…MIT.html> ;
    dcterms:hasVersion "0.1.0" ;
    prov:wasGeneratedBy tacat:build-activity .

tacat:build-activity a prov:Activity ;
    prov:used            tacat:reference-data ;
    prov:wasAssociatedWith tacat:software .

Same idea, expressed in RDF so it is queryable alongside the data, and with a provenance chain rather than just attributes.

DCAT is the W3C vocabulary for describing datasets in a catalogue. DCAT-AP+ is the NFDI extension that adds the processes and agents involved in creating a dataset; PROV-O is the W3C provenance vocabulary — entity, activity, agent, and the relations between them.

This matters more here than the 15 lines of Turtle suggest. NFDI4Cat’s phase-2 work (CoreMeta4Cat, ChemDCAT-AP) is built on DCAT-AP+, so a small correct envelope signals awareness of the consortium’s current infrastructure without attempting to implement the whole profile.

Where this one is currently weak

The PROV block is well-formed — and static. Nothing records which build produced this graph: no commit SHA, no source checksum, no version stamp (GAPS_0.md G3).

That is a pointed gap given the assessor’s stated position that semantics should be produced by the workflow rather than added afterwards as documentation. A provenance envelope that cannot say what generated the artefact is the documentation-shaped version of the thing he argues against.

Deliberately not a timestamp. A wall clock would have broken the byte-identical reproducibility above on the very first commit. A commit SHA and an input checksum identify a build far better than a clock does anyway — the two gates constrain each other, which is the kind of interaction worth noticing.

The house style — uv_build backend, requires-python = "==3.13.*", PEP 735 dependency groups, ruff at 120 columns with docstring and security rules on, strict mypy, Conventional Commits, CITATION.cff — deliberately mirrors the assessor’s own published packages. In this field software is treated as a citable research output, which is why a citation file and a changelog are not ceremony.

Chapter 5 in four lines
  • rdflib is SQLite for RDF: correct here, not production, and the repo says so.
  • Reason at build time; the runtime image ships no JVM and starts with the graph loaded.
  • CI’s middle stage gates the data, not the code — an image can build perfectly around a wrong graph.
  • DCAT/PROV describe the dataset itself; the provenance content is currently static, and that is a real gap.

That is the computing stack. The next three chapters are the chemistry — no prior knowledge assumed, and the reason every modelling decision above is what it is.
