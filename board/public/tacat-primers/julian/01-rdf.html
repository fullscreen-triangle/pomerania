Chapter 1

RDF as a database

RDF is a graph database with two unusual commitments: every identifier is a URL that means the same thing everywhere, and edges cannot carry properties. The first is what makes the project interoperable. The second is what forces its central modelling decision.

1. The only data structure

RDF has one construct. A triple: subject, predicate, object. That is the entire data model — there are no tables, no documents, no columns, no nesting.

Subjecttacat:PART_0000002_01
→
Predicatetacat:participatingEntity
→
Objecttacat:CHEBI_57972

Read it as a sentence: this participant node has, as its participating entity, the thing identified as CHEBI:57972. A set of triples is a directed labelled graph; the object of one triple is very often the subject of the next, and that is how structure emerges without any container construct.

Subjects and predicates are always IRIs. Objects are either an IRI (making the triple an edge to another node) or a literal — a string, number, date — which terminates that branch. That asymmetry matters more than it looks; it comes back in §6.

What you'd write in SQL 
CREATE TABLE participant (
  id        TEXT PRIMARY KEY,
  entity_id TEXT REFERENCES entity(id),
  role_id   TEXT REFERENCES role(id),
  coeff     NUMERIC
);

Shape is declared up front and enforced on write. A row that violates it is rejected.

The RDF equivalent 
tacat:PART_0000002_01
    a                        tacat:ReactionParticipant ;
    tacat:participatingEntity tacat:CHEBI_57972 ;
    tacat:participantRole     tacat:Reactant ;
    tacat:stoichiometricCoefficient 1.0 .

Shape is not declared or enforced anywhere. Any subject may have any predicate. Adding a nonsense triple is legal and silent — which is why SHACL exists.

2. Identifiers are global, and that is the whole point

In your systems, user_id = 42 is meaningful inside one database and meaningless outside it. Two services that both have a users table share nothing; reconciling them is an integration project.

In RDF, the identifier is a URL, and it is intended to be the same URL everyone else uses: 

http://purl.obolibrary.org/obo/CHEBI_57972      # L-alanine, in ChEBI's namespace
http://rdf.rhea-db.org/19453                    # a reaction, in Rhea's namespace
http://purl.uniprot.org/enzyme/2.6.1.2          # an enzyme class, in UniProt's namespace

These are PURLs — persistent URLs, run by the institution that curates the data, guaranteed stable and redirected to wherever the resource currently lives. When this project writes a triple pointing at CHEBI_57972, it is pointing at the same node that UniProt, Rhea and several thousand other datasets point at. No integration step, no mapping table.

Why this is the load-bearing decision

Chapter 2 shows a query that joins this project’s local graph against Swiss servers holding UniProt and Rhea, live, and gets back real protein counts. It works for exactly one reason: both sides use the same URLs as keys. Had the project minted tacat:Alanine instead, the join would return zero rows — and, as always here, no error.

The community rule for this is OBO Foundry principle FP-005: import terms that are out of scope, don’t invent them. Minting your own identifier for water instead of using CHEBI:15377 is, in this field, the fastest way to be dismissed.

Prefixes are import aliases

Writing full URLs is unbearable, so every RDF syntax has a prefix mechanism. It is exactly an import alias and has no semantic content: 

@prefix tacat: <https://w3id.org/bitspark/tacat/> .
@prefix rdf:   <http://www.w3.org/1999/02/22-rdf-syntax-ns#> .

tacat:CHEBI_57972 rdf:type <http://purl.obolibrary.org/obo/CHEBI_57972> .

# means exactly:
# <https://w3id.org/bitspark/tacat/CHEBI_57972>
#     <http://www.w3.org/1999/02/22-rdf-syntax-ns#type>
#     <http://purl.obolibrary.org/obo/CHEBI_57972> .

tacat:CHEBI_57972 is a prefixed name; it expands by string concatenation. One consequence bites in practice: a prefixed name cannot contain characters that would break the grammar. An unescaped / in the local part is a parse error — which is precisely the bug that made one of the first submission’s advertised example queries return HTTP 400 to anyone who copy-pasted it.

3. The difference from Neo4j that changes everything

If you know property graphs, RDF looks familiar until you try to put data on an edge.

Property graph (Cypher) 
CREATE (r:Reaction {rhea: 19453})
      -[:HAS_PARTICIPANT {
          role: 'reactant',
          coefficient: 1.0
        }]->
       (e:Entity {chebi: 57972})

The relationship is a first-class object with its own key/value properties. Role and coefficient live on the edge, which is where they belong.

RDF 
tacat:REACT_0000002
    tacat:hasParticipant tacat:CHEBI_57972 .

# ...and now where do the role and the
# coefficient go? There is no third slot.
# A triple is exactly three things.

RDF edges carry no properties. A predicate is an IRI and nothing else. There is no attachment point.

This is not an oversight; it follows from the triple being the atom. The standard workaround is the n-ary relation pattern — W3C published a note on it — and it will be familiar the moment you see it, because you have written it a hundred times.

You already know this as a join table

A many-to-many relationship with attributes on the relationship itself cannot live in either end’s table, so you create a third table for it: order_line between order and product, carrying quantity and unit_price. Nobody thinks of that as a workaround; it is just how you model a relationship that has its own facts.

RDF needs the identical move for the identical reason, and calls the intermediate node a bridge node. ReactionParticipant is order_line.

Here it is as the project actually writes it — one reaction, one of its four participants: 

tacat:REACT_0000002 a tacat:BiochemicalReaction,
                      <http://rdf.rhea-db.org/19453> ;
    rdfs:label       "alanine transaminase reaction" ;
    tacat:catalysedBy    tacat:EC_2_6_1_2 ;
    tacat:hasParticipant tacat:PART_0000002_01,
                         tacat:PART_0000002_02,
                         tacat:PART_0000002_03,
                         tacat:PART_0000002_04 .

tacat:PART_0000002_01 a tacat:ReactionParticipant ;
    rdfs:label                      "L-alanine as reactant" ;
    tacat:participatingEntity        tacat:CHEBI_57972 ;   # what
    tacat:participantRole            tacat:Reactant ;      # in what role
    tacat:stoichiometricCoefficient  1.0 .                 # how many

Four participants per reaction, each a node carrying what / in what role / how many. Chapter 6 explains why that role slot is not a nicety: substrate and product are not properties of a molecule, they are roles it plays in a given direction, and the same molecule flips between them across reactions and even across organisms.

Worth knowing: this choice is contested

NFDI4Cat’s own reaction ontology, Reac4Cat, models roles a different way (a BFO-style role pattern) and does not use n-ary participation. BioPAX and SBML both do use bridge nodes; Rhea uses a third approach again, numbering sub-predicates (rh:contains1, rh:contains2…). There is no settled answer, which means “I chose the n-ary pattern because it carries stoichiometry, and here is when I would switch” is the defensible position — not “this is the right way”.

4. Four file formats, one graph

RDF is a data model, not a file format. The serialisations are interchangeable — parse any of these, emit any other, and the triples are identical. This trips people up constantly, so it is worth seeing once. All four below encode the same single statement.

Turtle — .ttl, what humans read and what this project ships

@prefix tacat: <https://w3id.org/bitspark/tacat/> .
@prefix rdfs:  <http://www.w3.org/2000/01/rdf-schema#> .

tacat:CHEBI_57972 rdfs:label "L-alanine" .

N-Triples — .nt, one complete statement per line, no abbreviations

<https://w3id.org/bitspark/tacat/CHEBI_57972> <http://www.w3.org/2000/01/rdf-schema#label> "L-alanine" .

RDF/XML — the 1999 original; verbose, still everywhere, and what Owlready2 emits

<rdf:RDF xmlns:rdf="http://www.w3.org/1999/02/22-rdf-syntax-ns#"
         xmlns:rdfs="http://www.w3.org/2000/01/rdf-schema#">
  <rdf:Description rdf:about="https://w3id.org/bitspark/tacat/CHEBI_57972">
    <rdfs:label>L-alanine</rdfs:label>
  </rdf:Description>
</rdf:RDF>

JSON-LD — RDF that is also valid JSON, so it survives a normal web stack

{
  "@context": { "rdfs": "http://www.w3.org/2000/01/rdf-schema#" },
  "@id": "https://w3id.org/bitspark/tacat/CHEBI_57972",
  "rdfs:label": "L-alanine"
}
Why JSON-LD is worth your attention specifically

It is the format a full-stack developer would actually reach for: it goes through JSON.parse, it sits in a document store, and a consumer who ignores @context entirely still gets usable JSON. That is also why it is the format the assessor’s own lab tooling uses (SciDatS represents scientific metadata as JSON-LD). If you ever need to bridge this world to a normal web application, this is the seam.

5. Reading Turtle properly

You will be looking at data/reactions.ttl, so the three abbreviations are worth five minutes. Turtle is just triples plus punctuation sugar.

TokenMeansExpands to
a “is of type” rdf:type
; same subject, next predicate repeats the subject
, same subject and predicate, next object repeats both
. end of statement group —
"x"^^xsd:string a typed literal —
"x"@en a literal tagged English —

So this real block from the project…

tacat:REACT_0000001 a owl:NamedIndividual,
        tacat:BiochemicalReaction,
        <http://rdf.rhea-db.org/21824>,
        tacat:TransaminationReaction ;
    rdfs:label "aspartate transaminase reaction"^^xsd:string ;
    tacat:catalysedBy tacat:EC_2_6_1_1 .

…is six triples, and one of them is not like the others:

REACT_0000001  rdf:type    owl:NamedIndividual .
REACT_0000001  rdf:type    BiochemicalReaction .
REACT_0000001  rdf:type    <http://rdf.rhea-db.org/21824> .   # the Rhea identifier, as a type
REACT_0000001  rdf:type    TransaminationReaction .           # <- nobody wrote this one
REACT_0000001  rdfs:label  "aspartate transaminase reaction" .
REACT_0000001  catalysedBy EC_2_6_1_1 .

The third triple was computed by a logic engine during the build and written into the file. Nothing in the source code asserts it. That is chapter 3, and it is the single thing that distinguishes this from a database with RDF-flavoured syntax.

6. The distinction that broke the first submission

Back to the asymmetry from §1: an object is either an IRI or a literal. To a JSON eye these look interchangeable. They are not.

A literal — text that happens to look like a URL 
tacat:CHEBI_57972
    tacat:chebiIRI
      "http://purl.obolibrary.org/obo/CHEBI_57972"
      ^^xsd:string .   # how this project first did it

A dead end. The graph stops here. A join against ChEBI matches nothing, because the other side has a node and this side has a string.

An IRI — an actual edge 
tacat:CHEBI_57972
    a <http://purl.obolibrary.org/obo/CHEBI_57972> .

An edge to a node that other datasets also reference. This is what makes a federated join return rows.

The failure, in full

An earlier revision of this project carried every external identifier only as an xsd:string. The graph validated. The tests passed — they checked the string was well-formed. The README claimed interoperability. And a federated query against UniProt would have returned an empty result set with a 200 OK.

The first fix emitted both: the literal, on the premise that sh:pattern in SHACL can only regex-check a literal; and an IRI, because only a node can be joined. The regression test asserts the object is a URIRef — not that some well-formed string is present, which is the check that gave false confidence the first time.

That premise was wrong, and it is worth knowing why. sh:pattern matches the lexical form of the value node, and for an IRI the lexical form is the IRI string. The literal copy validated nothing the IRI could not validate itself, so it was deleted.

Why rdf:type, and not owl:sameAs or skos:exactMatch

owl:sameAs is a logical identity claim: a reasoner is licensed to merge everything either side asserts. Point sameAs at a ChEBI term and you have, formally, pulled all of ChEBI’s assertions about that molecule into your graph — including any you never reviewed.

skos:exactMatch is the weaker mapping assertion, and this project used it for a while. It is still wrong here: SKOS mapping properties are sub-properties of skos:semanticRelation, whose domain and range are both skos:Concept — so the graph was entailing that ChEBI terms and our nodes are thesaurus concepts, and it was pointing an individual at a class.

rdf:type makes neither claim. The ChEBI term is a class; our node is an instance of it. One triple, exactly true, joinable, and still validated by the same shape.

7. Blank nodes, and why this project bans them

RDF permits anonymous nodes — a node with no IRI, valid only inside one document. Turtle writes them with square brackets: 

tacat:REACT_0000002 tacat:hasParticipant [
    tacat:participatingEntity tacat:CHEBI_57972 ;
    tacat:participantRole     tacat:Reactant
] .

Convenient, and a trap. A blank node has no stable identity, so merging two graphs that each describe “the same” participant produces two nodes, silently — and any aggregate query then double-counts. It is the auto-increment primary key of RDF: fine until data crosses a system boundary, at which point you cannot deduplicate.

Every bridge node in this project therefore gets a real IRI (tacat:PART_0000002_01), and the SHACL shapes enforce it with sh:nodeKind sh:IRI so a regression fails the build rather than quietly corrupting a count.

Chapter 1 in four lines
  • One data structure: the triple. No schema is enforced by the model itself.
  • Identifiers are global URLs, which is what makes cross-dataset joins possible at all.
  • Edges carry no properties → a bridge node, exactly like a join table with attributes.
  • An identifier stored as a string rather than a link is unjoinable, and fails with zero rows and no error.
